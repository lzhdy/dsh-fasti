## 0. 一句话目标与结论

【目标】正常使用阶段，记忆的沉淀与检索**运行回路零人工**：既不需要人逐条决定建卡，也不设置“机器起草、人点确认”的常驻审核岗。人的合法位置只在工程期（定规则、标一次性金标、按数据外审解冻冻结项）。

【结论】该目标当前**尚未实现，但路径在结构上成立**，依赖两个相互独立、有先后顺序的后续专项：

1. **专项一（P2）锚点写入侧治理**：在写入链路上闸，保证增量事件的 anchors 只能是真实经历 ULID，从根上消除“悬空锚点”这类人工补救的复发条件。改动集中在事件写入链，可独立验收。
2. **专项二（运行期自动建卡链路）**：把 v1 离线 builder 的确定性派生能力装配到宿主既有的异步 worker 上（人工 seed 能力已删除，见文首现状更新），并由 #42 补齐自动建卡判断，使 ready 事件确定性地沉淀为记忆卡。其结构化字段已可全自动，唯一未决难点是自然语言检索词（cue/alias/discriminator）如何不违反 K5 而自动化，须由 v1 人工金标 + harness 数据裁决，不能在本期臆断。

【事实】记忆层 v1（`memory-v1-offline-scaffold-plan.md` §0.1、§1.1）自我定位为**离线脚手架**：“运行时自动建卡/LLM 静默改写”明确在本期 out 清单。本文承接该 out 项的立项论证，不改变 v1 范围。

## 1. 现状证据：缺口在哪、为什么历史上没拦

### 1.1 anchors 的设计定位与生产链

- 【事实】事件契约头注释明示“**anchors 第一期生成但不消费（任何逻辑不得读它做判断）**”（`src/contract/event.ts:8`）；LLM 端口同样标注“事件锚点（第一期生成但不消费）”（`src/event/llm-port.ts:32-33`）。即 anchors 最初是 LLM 产出的预留字段，内核一期没有任何逻辑读取它，因此契约只保数组形状、不保语义。
- 【事实】契约校验入口 `parseEvent` 对 anchors 仅做字符串数组校验：`anchors: requireStringArray(...)`（`src/contract/event.ts:510`），**无 ULID 形态、无经历存在性、无时间窗校验**。字段白名单含 `'anchors'`（`event.ts:246`）。
- 【事实】anchors 的实际生产者是摘要 LLM：端口接口 `LLMPort.summarize` 返回自由字符串数组（`src/event/llm-port.ts:76`），真实模型适配在 `src/adapters/dsh/llm.ts`（内核零生产依赖，端口只定义接口）。
- 【事实】事件闭合慢路径把 LLM 返回值**原样透传**落为新版本：`anchors: [...response.anchors]`（`src/event/closure.ts:375`，`writeSummary` 内），随后 `appendVersion(next)` 追加 events 二级真源（`closure.ts:388`）。摘要重写/修正路径也会刷新 anchors（`src/event/correction.ts:109` 注释“只更新锚点/话题线”、`:570-579`）。
- 【事实】events 是 append-only 二级真源，落版即固化、无 update/delete 原语（`src/contract/frozen-surface.ts:18-24`、`:78-89` 禁能力清单）。因此历史已落版的语义标签**不能原地改**，只能追加新版本，或在可重建投影层处置——这正是记忆层 v1 路径 A（投影层 remap-anchors）不回写真源的原因。

### 1.2 问题如何在记忆层首次暴露

- 【事实】记忆层 v1 是第一个真正**消费** anchors 的模块：builder/seed 要求每个锚点能回查到 `experiences/` 中的真实经历 id，否则抛 `MemoryAnchorDanglingError` 零产物。真实数据中 7 个闭合事件的 anchors 是 LLM 生成的中英文语义标签（如“煮冻饺子”“web_search”），与 252 条经历的 26 位 ULID 无任何映射，去重后形成 34 个悬空锚点；另有 1 个事件 anchors 为空。
- 【事实】该缺口属于写入侧数据治理，不是 builder/seed 的缺陷——读取侧 fail-fast 行为符合方案规定的唯一硬失败。

### 1.3 可直接复用的既有能力（无需新造轮子）

- 【事实】ULID 形态判定已存在且零依赖：`isUlid()`（`src/core/ulid.ts:117`，26 位 Crockford、首字符上限等）。
- 【事实·2026-11-12 更新】原 `src/memory/anchor-remap.ts`（`candidateExperienceIds` 候选池纯函数与 ULID/存在/池内三校验）与 `src/memory/seed.ts`（真值三关 H9）已随人工通道整体删除，**不能再 import 或当作既存能力**；P2-L2 与专项二需要的候选池/池内校验须在收窄基线上重新实现。当前仍在、可直接复用的是：`src/memory/builder.ts` 步骤 4 的悬空硬失败（每个 anchor 必须 `isUlid` 且存在于真值经历全集，否则 `MemoryAnchorDanglingError`、零产物）、`src/memory/serial.ts` 候选序号化，以及上文 `isUlid()` 与契约双模校验范式。
- 【事实】反幻觉候选序号化已落地：`buildSerialMap/resolveSerials`，未知序号拒绝并允许一轮重取、禁止猜序号（`src/memory/serial.ts`，源自 Mem0 教训，见脚手架方案 §4.7）。
- 【事实】写入侧校验的双模范式现成：`assertKnownFields` 仅在 `mode==='write'` 收紧、read 模式对旧数据宽容（`src/contract/validate-experience.ts:73-88`）；契约内本地校验函数 `parseSummary` 的 fail + 硬上限写法可作 anchors 校验的同款范式（`src/contract/event.ts:549-563`）。

## 2. 专项一：P2 锚点写入侧治理（拦增量）

### 2.1 治理目标与不可越界

【建议】目标：自治理版本起，**新追加的任一事件版本，其 anchors 在落真源之前必须通过形态与引用校验**，使“语义标签型锚点”无法再进入二级真源。历史已落版数据不回写、不迁移，守住 `source-append-only`；原“由 v1 路径 A 在投影层一次性处置”的机制已删除（见文首现状更新），历史悬空锚点改由专项二 #42 自动建卡合规消解，在此之前 builder 对其硬失败、零产物且无人工绕行。

【硬边界】

- 不修改、不删除任何已存在的 events/experiences 记录，只在新 append 链路上加闸。
- read 解析模式保持宽容（旧数据、未来版本可读），仅 write 模式收紧，沿用 `assertKnownFields` 双模惯例，避免读取历史真源时被新校验反向打爆。
- 不新增生产依赖（`isUlid`、候选池均为内置/既有纯函数）；不向 events 真源表加列（对齐脚手架 §0.2 与 event-schema 冻结）。

### 2.2 建议的三层闸门

【建议】按“能否在当前层拿到所需上下文”分三层，越界校验放在拿得到全集的一层，不把跨记录查询硬塞进单记录契约。

- **L1 形态闸（单记录、无外部依赖，落点 `src/contract/event.ts` 的 write 解析）**
  - write 模式下 anchors 每一项必须过 `isUlid()`；非 26 位合法形态当场 SchemaError，拒收该版本。
  - 与 `parseSummary` 同构，新增本地 `parseAnchors()`，不引入 I/O 与集合依赖。
  - 【开放】是否允许 `anchors=[]` 的 ready 事件：现状真实数据存在 1 个空锚闭合事件。需在评审中定性——空锚是合法“暂无可引用经历”状态，还是 ready 必须非空；该决策决定 L1 对空数组的口径，本文不预设。
- **L2 引用完整性闸（跨记录，落点闭合慢路径 `src/event/closure.ts` 写版本之前）**
  - 在能读取 `experiences/` 全集的位置，对每个 anchor 做存在性校验，并以候选池逻辑校验其属于“同通道、occurred_at 落在事件 [起,止] 闭区间”的候选池（原 `candidateExperienceIds` 已随 anchor-remap 删除，本闸需在 P2 重新实现该纯函数，见文首现状更新）；池外/不存在即拒绝。
  - 失败语义沿用闭合慢路径既有纪律：抛错按一次失败处理、退避重试，连续失败标记 permanent 并保持事件 pending（参考 `src/adapters/dsh/llm.ts:129-160` 的 worker 失败约定与 `closure.ts:391` 起的失败处理），**不得用占位锚点糊过去、不得写半份坏版本**。
- **L3 生产端反幻觉（治源头，而不是只在末端拒收）**
  - 【建议】不让 LLM 自由生成 id：摘要请求改为下发“窗内候选经历序号表”，模型/流程只能回候选序号，再由 `resolveSerials` 映射回 ULID；未知序号拒绝并允许一次重取，二次仍失败则本轮不带锚点按失败处理。这样把“自由文本标签”从生产端根除，而不是依赖 LLM 自觉吐对 ULID。
  - L3 涉及摘要 prompt 与端口契约调整（`llm-port.ts`、`adapters/dsh/llm.ts`），属 B 块摘要链范畴，应与 L1/L2 分批改、独立评审。

【建议】`src/event/correction.ts` 的锚点刷新路径必须与闭合路径纳入同一套校验，避免出现“闭合被拦、修正能写”的旁路。

### 2.3 验收与反证要求（沿用记忆层方法学）

- 正反例表驱动单测：合法 ULID 落版、非 ULID/池外/不存在锚点在 write 模式整份拒绝且零追加；read 模式读取含旧标签的历史真源不报错。
- 注入变异自证：临时摘除 L1/L2 任一闸门，对应拒收用例必须变红，逐字节还原后回绿。
- 全量 `npm run verify` 绿、Linux 0 skip；真实根只读演练先于任何写授权。
- 兼容性证据：对当前真实 events 文件做只读回放，确认新校验不影响既有版本读取，只约束未来 append。

## 3. 专项二：运行期自动建卡链路（去运行期人工）

### 3.1 先厘清哪些已经可以全自动、哪个是真难点

【事实】v1 记忆卡的字段分两类：

- **结构化/派生字段**：`card_id`、`anchor_json`、channel、时间窗、初始 weight/hit_count（恒 0）、失效时间戳（NULL）等，已由 `builder.ts` 从真源**确定性派生**，重放幂等、双跑逐行相等。这部分天然不需要人。
- **自然语言检索词字段**：displayCues、aliases、discriminator、sensitive（即 L0 人工标注）。v1 因两条约束只能人工产出：① H7 子串反查禁止把 summary 整句抄进卡（脚手架方案 §4.7）；② K5 禁止 LLM 静默生成/改写已存事实卡（§10.2，无重议触发条件）。

【建议】因此“自动建卡”不是一个二选一开关，而是先把结构化部分自动装配跑通，再单独、谨慎处理检索词自动化。

### 3.2 合法挂载点：复用既有异步 worker，不碰摄入热路径、不建调度器

- 【事实】现有架构中，摄入热路径只做内存入队、不 await 不写盘（`src/api/index.ts:535-539`、`:611`），闭合后的 LLM 摘要在异步慢路径由宿主后台 worker 一轮轮 `drain()` 驱动（`src/adapters/dsh/llm.ts:143-160`、门面 `drainClosure` 于 `src/api/index.ts:649`，`:591` 注释明确“由宿主的后台 worker 周期调用”）。内核本身**无常驻定时器/cron**，所有真源写经单写者 `WriterQueue` 串行（`src/source/writer-queue.ts:13-38`）。
- 【建议】未来记忆自动阶段沿用同一条宿主 worker 链路：新增一个与 closure drain 同构的“记忆投影 drain”，在事件进入 closed+ready 后异步触发，对独立投影目录 `projection/memory-index/` 做增量/重建写。它：
  - 不进对话摄入热路径（守 K8：LLM 判定不进摄入热路径）；
  - 不在内核新建常驻调度器（守 K3：调度归宿主外部 tick，内核只暴露可被调用的 drain 能力）；
  - 只写可整体删除重建的投影，绝不写 append-only 真源（守 `source-append-only`、`projection-rebuildable`）。

### 3.3 必须正面处理的架构门：M6 静态隔离

- 【事实】记忆层 v1 设有双向 import 门并带投毒自证：规则①实时链路不得 import memory；规则②memory 不得 import 门面（`tests/memory/schema.test.ts:280-461`，含静态扫描与六类违规探针）。
- 【建议】自动建卡接线**必然要重新讨论规则①的依赖方向**，但不得在实现 PR 内偷偷改测试。正确做法是立项时明确装配层归属（大概率由宿主 adapter 或新增 C 块装配模块依赖 memory 的纯函数，`src/api` 内核仍不直接依赖 memory，memory 仍不反向依赖门面），随之显式修订 M6 门的允许边界并补新的投毒用例，走与 K 项同级的评审。

### 3.4 检索词自动化：列为待验证假设，而非既定方案

【事实】K5 永久禁止“LLM 静默改写已存事实/卡”，其原文保留的唯一出口是“LLM 输出只能经人工种子流生成新决策行”（脚手架方案 §10.2 K5）。K8 对热路径 LLM 判定设了严格的数据触发条件。任何检索词自动化都牵涉这两条冻结项，不能默认放行。（2026-11-12 更新：人工种子流已删除，脚手架 K5 出口已改写为“经她的决策留痕生成新决策行、出口为 #42 自动建卡”；K5“禁止静默改写、必须显式决策留痕”的约束本身继续有效。）

【建议】给出两条都需数据验证、且不违反冻结面的候选方向，本期不选定：

1. **确定性抽词先行（零模型）**：从事件已有的 `key_points` 等结构化/短词字段，按规范化与长度规则确定性抽取 cue/alias，不调用 LLM、不复制 summary 整句（仍过 H7 子串反查）。能跑通的部分先实现零模型自动化，覆盖面不足处再议。
2. **受约束模型候选 + 离线门禁（不进运行回路自由发挥）**：若必须借助模型，模型只能在给定候选内按序号选择（复用 `serial.ts` 反幻觉协议），其产出先当作离线候选，用 v1 的 L0 人工金标做 R1/R2 对照，达到脚手架 §2.2 红线（R1≥0.85、R2≤0.05）并有 bootstrap 置信区间支撑后，才按 §10.2 规定走外审解冻；解冻前不得进入自动写路径。

【开放】在零人工前提下检索词质量能否达标，当前 252 经历/10 事件属小样本，统计上不足以下结论（脚手架 §6.1 已要求 holdout/LOEO 与置信区间、证据不足不得宣称达标）。本提案不承诺“一定能去掉人工”，只承诺“是否去掉由可复算数据裁决，而非由人长期顶岗”。

### 3.5 运行期质量保障：机制兜底，而非机器审核岗

【建议】呼应“不应存在单纯机器审核”的要求：运行期不增设“AI 审核 AI”的判断节点，质量由三类客观机制承担——

- 写入/构建期的确定性硬门（ULID/存在校验、悬空硬失败、原子写、append-only 账本；原 H9 三关随 seed 删除，候选池护栏待 #42/P2 重建），违约整份拒绝；
- 离线 harness 的可复算指标 R1/R2/R3、DRM 诱饵、provenance 100% 硬失败、变异反证（脚手架 §6）；
