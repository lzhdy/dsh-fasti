## 0. 给外部评审者的背景（三分钟版）

**这个系统是什么**：fasti 是一个长期运行的 AI 主体（下称"她"）的持久记忆层。三段流水线：①原文员把每轮对话原文落盘；②复盘员（唯一用 LLM 的环节）把一段对话折叠成一条"经历"，并同时产出 1–3 条检索线索（cue）；③卡片员（纯规则、零 LLM）把已闭合且质量就绪的经历投影成"记忆卡"写进 sqlite 索引。卡能被搜到的文本**只由 cue 和别名拼成**，正文不进索引，检索走 SQLite FTS5（trigram）。

**检索侧**：BM25 粗召回 → 布尔词面门（别名精确命中直接过；FTS 子串命中要求过 ASCII 词边界；LIKE 回退构造性拒绝）。宁可返回"没找到"，也不给弱匹配凑数。

**三种运行状态**：`off`（不建卡不检索）/ `shadow`（正常建卡，检索照跑但不把结果交给她，只写观测日志）/ `on`（检索结果进入对话）。当前已切到 `shadow`（见第 9 节）。

**mem_miss 是什么**：她主动调用检索工具却没搜到东西时，系统往一张叫 mem_miss 的"落空案底"表里同步写一行。它记录的是"她问了什么词、什么通道、什么时刻、返回几条"，**不记录对话正文**，词面只存规范化结果和 sha256，不存原始查询全文。

**本文要评审的**：这张案底表的**留存裁剪机制**（怎么删旧行、在哪删、删了怎么记账、上限怎么定）。它该不该存在已经裁定保留（有四个下游消费者要吃这份数据），不是本次评审议题。

**硬约束（违反即方案不可行，请勿建议）**：

1. 禁止新增守护进程、定时器、`fs.watch`——系统由宿主节拍驱动，没有后台常驻进程，这是架构冻结条款（K13）；
2. 禁止新增表、禁止新增真源字段——真源是 append-only 冻结面；
3. 内核零 LLM：所有派生与裁剪必须是纯规则、可重放；
4. 不得在对话主链路上新增"大事务"式清理（会拖慢每轮响应）；
5. 不允许为了采集标定数据而提前翻转三态开关；
6. 现有离线重建 CLI 是唯一的维护入口，不建议为运维再造第二套入口。

**期望的输出格式**：每个意见按「结论 / 依据 / 可执行替代」三段写。反对某个裁定必须给出替代方案，不接受"感觉不合适"。

## 0.1 大白话版（同一件事的通俗说法，可跳过）

有一张叫 mem_miss 的"落空案底"表：她每次想搜记忆却没搜到，就同步往里面写一行。这张表现在只增不减、不去重、重建索引时整表原样搬。短期没事，但它没有任何上限，跑久了文件只涨不缩，重建越来越慢，而且插入发生在对话返回前的主链路上，将来量大了还可能拖慢每轮对话。

查代码后有两个让问题变简单的事实：①这张表**生产环境只写不读**，没有任何运行期逻辑靠它做判断，删旧行不影响任何在线功能，只影响离线审计能回看多久；②数据根刚清零，现在一张真实行都没有——所以现在拍任何数字都是瞎拍，正确做法是先把"将来怎么删、在哪删、删了怎么记账"设计死，常数等影子期攒够数据再填。

## 1. 现状实证（HEAD 4690032）

- E-1 表结构（`src/memory/schema.ts:85-95`）：8 列——id(ULID)、term_norm（规范化词面，**非原始查询全文**，M11 纪律）、term_hash(sha256 hex)、channel、anchor_event_id/anchor_json（v1 恒 null，待 #116）、returned_count（运行期恒 0）、observed_ms；两个索引 idx_miss_time、idx_miss_hash。

- E-3 主链路同步写（`src/assembly/memory-tools.ts:191-213` → `store.recordMiss` → insertMissRow）：落空登记是对话返回前的**同步单行 sqlite 插入**；唯一冒泡抑制点是该函数 try/catch（失败只入案底不阻断对话），**对插入耗时无任何兜底**——即 11.6 挂账的"同步写时延无兜底"观察项，与本卡同一假设的两面。
- E-4 **生产零读取**：全仓 src/ 与 scripts/ 无一条 `SELECT ... mem_miss`；读取者仅测试与 rebuild 搬运（`builder.ts:202/432`）。run-memory-audit 写独立 `--out` 库、不读生产 mem_miss。结论：留存裁剪的运行期爆炸半径为零，影响面仅离线审计/统计的历史回看深度。
- E-5 rebuild 行为（`src/memory/builder.ts:425-440`）：重建在一个事务内 `copyRows('mem_miss', ...)` 全量原样搬运，行数线性进入重建耗时；这是"无限增长拖慢 rebuild"的具体机制，不是推测。
- E-6 仓内留存先例：内存环形缓冲 FAILURE_BUFFER_LIMIT=100（closure.ts，纯内存不落盘，不可直接照搬）；channel 契约有 retention_days 配置形状（contract/channel.ts，跨域仅作命名参考）；投影有整库清空与 FTS 单行 DELETE；**memory 层无任何 sqlite 行级留存/DELETE/VACUUM 先例**，也无定时器/守护进程（K13）。

## 2. 策略选项（机制层，常数另立标定）

| 方案 | 机制 | 优点 | 代价/风险 |
|---|---|---|---|
| A 按天数留存 | 删 observed_ms 早于 cutoff 的行，idx_miss_time 直接支持 | 回看窗口稳定可解释；与 Q4"≥2 周同口径段"天然同构；实现最简单 | 高频爆发期窗口内行数仍可能冲大，rebuild 成本无硬上界 |
| B 按行数上限 | 只留最新 K 行 | 表体积/rebuild 成本有硬上界 | 高频期历史被加速淘汰，统计窗口随负载伸缩，恰好在最需要长窗数据时丢数据 |
| C 双闸 hybrid（推荐） | 天数窗口为主、行数硬顶为安全闸，谁先触发听谁 | 常态保稳定回看窗，异常爆发有硬兜底；两个都是工程期命名常量、无新表 | 两个常数都要标定；语义需写清"行数顶触发时窗口缩短"要进观测 |
| D 压缩/rollup | 老行按 (term_hash, channel, 日) 聚合成计数行后删明细 | 保留频次分布统计价值、体积有界、可顺带丢弃 term_norm（隐私更严） | 要新表或新行形态、改 rebuild 与审计口径、丢事件级 id/时间精度；churn 最大，与"不新增表"冻结面有张力 |

**主控建议：v1 取 C（hybrid 双闸），D 挂账。** 理由：E-4 证明运行期零读取，A/C 级别的简单 DELETE 不损失任何在线能力；D 的统计价值在没有消费者的当下是预留设计，违反 YAGNI，等 #92 漏召 CLI/统计审计层真要吃长窗频次时再做，届时本卡 C 的行数顶保证它不会在等待期失控。

## 3. 执行缝合点（不添守护进程的前提下去重）

- **首选缝合点：rebuild 事务内裁剪**。builder 本就全表重写，copyRows 改为带 cutoff/limit 的搬运几乎零新增机制，天然 level-triggered、无定时器、无新写柄、不触 M6 白名单扩容；裁剪与重建同事务，不会出现删了一半的中间态。
- **不选**store 打开即删（在对话主链路启动路径上加 DELETE 大事务，把 rebuild 的锅甩给首轮延迟）与独立 prune 守护进程（违反 K13）。
- **Q2-a 已定**：CLI 只加只读 `--dry-run` 报告，删除只随 rebuild 发生，保持删除面唯一；不给脱离 rebuild 的独立删除入口。
- **Q2-b 待实测**：sqlite DELETE 不缩小文件（页内复用，增长停止但体积不回落），要物理回收需 VACUUM。默认不做运行库 VACUUM；若实测发现 builder 确实是"写新库→原子替换"，旧文件整体删除即等价回收，此问题自然消失（该前提见 P-8，尚未实证）。
- **Q2-c 已定**：mem_miss 是客观案底，批量裁剪属可审计动作，须仿修订账本在 decisions 台账留一条裁剪记录（cutoff、删除行数、剩余行数、revision），不允许静默删除。

## 5. 标定计划（G-4 落地：先有数据再定常数）

影子期不改变任何生产行为，只做测量与沉淀。**数据源订正（E-10④）**：shadow 态 mem_miss 本体零写入，落空事件种群落在 shadow-observations.jsonl，标定期以该日志的 no-match/abstain 事件同义换算"若在 on 态会产生多少 mem_miss 行"，不允许为采数提前翻转三态开关。测量项全部走只读 SQL/离线脚本，不新增运行期写面：

1. 行数增长（以 shadow 日志换算）：每日落空事件数、按 term_hash 的重复分布（去重后集合大小 vs 事件数，验证"行数倍增而集合稳定"的实际比例）；主动工具调用与（#116 通电后的）自动窗口裁决分桶统计，响应 E-11 双工况；
2. 体积：单行平均字节（含两索引摊薄）、库文件体积随行数曲线、DELETE 后页复用率与是否需要 VACUUM；
3. rebuild 成本：rebuild 耗时对 mem_miss 行数的弹性（确定"拖慢"的拐点）；
4. 主链路时延：recordMiss 单行插入耗时分位（p50/p95/p99），回答 11.6 观察项；
5. 窗口形状：达到 Q4 门槛（2 周/四态各 200）时回看，14/30/60 天窗口各自行数与体积，作为天数闸候选值的实测依据；行数顶取观测期 P99.9 日增量×窗口天数的安全倍数。

**定稿闸口**：常数在 #91 Q4 验收前的一次单独评审中冻结，写入 params 风格的命名常量并注释数据来源；在此之前 TDD 只落机制（裁剪纯函数、rebuild 接线、台账记账、红测），常量位允许放显式标注"待标定"的保守临时值且必须有红测锁定其临时身份，禁止把临时值叙事成定稿。
