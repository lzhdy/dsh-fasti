## 〇之前 · 评审 P0 / P2 修复（第二轮交付）

### P0 · 任务闭环信号被直接激活，违反 §5.2 的 dormant 状态

**评审结论**：真实数据上 dry-run 产出 21 段（14 task-closure + 7 silence），
冻结夹具是 8 段（7 silence + 1 open），A11 无法通过。

**根因（实现方确认）**：上一轮把「阶段 0 类型化 + 作用域级判据落地并经用例验证」
当成了自动激活，漏掉了设计稿要求的**显式口径变更**。定案稿 §5.2 原文：

> **「休眠」是显式状态，不是一句注释。** ……阶段 0 类型化 + 作用域级判据落地并经用例验证后，
> **才把该信号从 `dormant` 改为 `active`**。

上一轮只在文档里写了「保持 dormant」，**实现里没有门控** —— 判据照常生效。
夹具生成器 `make-fixture.py` 的口径也印证了这点：其文件头明确写
「**任务闭环 dormant，不参与**」。

**修复落点**：

| 项 | 落点 | 内容 |
|---|---|---|
| 开关字段 | `src/event/params.ts` → `EventParams.taskClosureActive: boolean` | 默认 **`false`**（dormant），常量单点 |
| 取值函数 | `src/event/params.ts` → `taskScopeActiveOf(params)` | 名字刻意避开字段名（纪律 6 守卫为朴素子串匹配） |
| 门控 | `src/event/segmenter.ts` → `mergeInto` | `taskScopeActiveOf(this.params) && isTaskScopeClosed(...)` |
| 作用域状态维护 | **不门控** | 判据始终可被验证；只有「是否参与闭合判定」受开关控制 |
| 关闭时行为 | — | 恒不产生 `task-closure`；闭合只由静默 / 两上限 / 场景切换触发 |
| 口径文档 | `docs/implementation-notes.md` §10.3 | 补「门控落点」小节 |

**激活路径**：由**设计口径变更**决定（`dormant` → `active`），实现方**不得**自行打开。
开关只提供「可被打开」的能力，默认值永远是休眠。
