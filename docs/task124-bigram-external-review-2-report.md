## 1. Q1 · 升版口径裁定：**有条件采纳**

**问题**：FTS 几何变更走库级 schema v3、卡行版本（MEMORY_CARD_SCHEMA_VERSION=1）不动，是否存在未识别的迁移/漂移漏洞？

### 1.1 成立的部分（为何不是不采纳）

- **卡行不动有先例、有道理**（E-6）：v2 先例已确立「库版本管库形态、卡行版本管卡契约」的解耦。本卡不改卡契约字段，只改派生索引的切分几何，卡行版本不跟是正确的。
- **迁移风险被架构天然吸收**：FTS 是「抄本可弃」的派生物（§3.5 / 4.4），真源（append-only 账本）零改动。v2→v3 无数据迁移，回滚＝还原 commit＋回 v2＋离线重建（§7），逻辑闭环成立。
- **版本门有红测兜底**（§5-6）：v2 库在 v3 代码下必须被识别为需重建、不得静默查询，且沿用 #123 P4 已验证的红测范式。「旧库静默混用」这一最大漂移漏洞已被测试封死。

### 1.2 三个条件项（漏洞在别处，须补）

**条件①：切换运行时序——「合并≠部署」。**
版本门的语义是「v2 库遇到 v3 代码即拒查」，这意味着 v3 代码一旦生效、而真机重建授权（挂账③）尚未执行，**整条记忆召回进入黑洞**。虽与「宁空勿错」哲学一致，但对长期运行主体（"她"）是可用性事件。charter §3.5 已把真机重建单列授权单，但未把**部署动作**与授权绑定。要求补一句运行手册性质的条款：

> v3 代码可合并入库，但真机生效（替换现役 v2 代码）必须与授权重建构成同一次原子切换；授权单在编码阶段并行起草，授权前 v2 代码保持可运行。

**条件②：重建幂等验收覆盖 FTS 抄本本身。**
§6 现有口径只有 `row_hash_sum` 逐字节相等——它验证的是真源/卡行重放，**不覆盖 FTS 文本列写没写对**。抄本写坏而行哈希照样通过。补一条：重建后（临时根合成库上）比对 FTS 文本列与 `cueTextOf → toBigramUnits` 重算产物逐字节相等（全量或确定性抽样，建议全量，2 卡量级成本为零）。

**条件③：承重不变量显式登记。**
本裁定成立的关键前提是「FTS 纯抄本、真源唯一权威」。建议在 §2 或 §3 把它写成显式不变量：**任何把 FTS 列内容读回卡契约/真源的改动，都视为违反本卡边界**。防未来重构悄悄把抄本变真源，届时 v3 升版口径整体失效。

### 1.3 顺带钉死的小口径

- 版本机械识别机制沿用现有版本戳/戳记即可（不新增表，符合 K5）；写明「机械识别＝既有 schema 版本戳比对」即可，不必扩表。
- `MIN_TRIGRAM_LENGTH`（projection/sqlite.ts，E-2）→ 新常量 `MIN_FTS_CODEPOINTS = 2`：charter §3.4 写「bm25.ts 改引新常量」，须保持**单一定义处**（建议落 types.ts 或 schema 邻近、两侧 import），防 v3 后两处阈值漂移。红测「阈值常量回 3 打红」已覆盖单点，但漂移形态是两处不一致，实现细则里点名即可。

## 2. Q2 · 宽窄边界裁定：**有条件采纳**

**问题**：片段枚举（拆句工）拆出本卡、留待金标标定，边界切分是否干净，有无本卡必须顺带解决的耦合面？

### 2.1 边界切分：干净，拆分正确

- 本卡＝**索引几何**（tokenize 单位、阈值、复核对象）；拆句工＝**查询侧多尺度碎片枚举＋聚合策略**（2–6 码点碎片、停用词表、宽松/严格聚合三参数）。拆句工天然以 `toBigramUnits` 的产物为原子单位，接口面已经存在，无隐藏耦合。
- 三参数留待 P6 金标（≥200 题）标定是**正确**的拆法：没有金标就定参数＝拍脑袋，本卡硬塞反而制造不可验收目标。非目标清单（§2.2）把口子都堵住了，范围蔓延防护到位。
- 对 #123 的解耦（接口面＝既有 display_cues_json）成立，两者可独立交付、独立回滚，§4 的陈述属实。

### 2.2 两个本卡必须钉死的口径（否则拆句工继承歧义）

**条件①：单字查询路由声明。**
unigram 双写的意义是让查询中的**孤立单字段**（如「蓉的发票」里的「蓉」）可经 FTS 命中；但准入阈值 2 码点把**纯单字查询**（1 码点）挡在 FTS 门外、走 LIKE 回退（回退路径语义不变，§3.4）。这个分工是合理的，但 charter 一字未提。后果：上线后任何人测「单字查不到」都会当成「2 字以下全灭」回归重演。要求：
- §2.1 或 §3.4 显式声明「1 码点查询走 LIKE 回退属预期行为，unigram 双写只服务多段查询中的孤立单字段」；
- 红测补一条：纯单字查询走回退路径且能命中（别名卡），多段查询中孤立单字段经 unigram 命中。

**条件②：复核归一化口径。**
`toBigramUnits` 含 NFKC（红测 1），匹配发生在归一化空间；而 §3.4 的复核对**原文**（display_cues_json＋活跃别名）做 matchesSubstring。若 needle 用原始查询串、靶用未归一化原文，全半角/大小写差异会**在门上吃掉 bigram 的召回增益**（索引命中→复核拒收）：例如查询 `Ｉｐｈｏｎｅ１５`（全角）归一化后命中索引里的 `iphone15`，复核却在原文 `iPhone15` 上做字面匹配而拒收。bigram 放大了「匹配空间与复核空间规约不一致」的既有缝隙（trigram 时代缝隙较小）。要求：
- 明确复核两侧同一规约（建议：两侧同做 NFKC＋ASCII case-fold 后再 matchesSubstring；或明确声明不做、接受该拒收）——二选一，写入 §3.4；
- 红测补一条：全半角/大小写变体的端到端行为与所选规约一致（红测 1 只覆盖切分函数，不覆盖复核路径）。

### 2.3 一个记录即可、不改语义的行为

**跨 cue 短语「歪打正着」**：cueTextOf 多 cue 拼接后，查询短语可能跨 cue 边界命中（同一张卡的两个 cue 恰好相邻）。对检索而言同卡命中通常有益，但行为依赖 cue 拼接顺序，不是严格语义。建议在实现说明里记录一句「跨 cue 相邻命中属已知旁效、视为召回增强、不修」，避免拆句工阶段被当 bug 返工。红测 3 已覆盖「不误撞**异卡**」，同卡跨 cue 不必加测。

## 3. Q3 · 时序裁定：**有条件采纳**

**问题**：本卡先于 #123 解冻、先于 P6 出题的排期，是否会产生返工或无效验收？

### 3.1 对 #123：零阻塞成立，返工风险低

- 接口面 display_cues_json 已存在（E-9），#123 管「cue 文本从哪来」、本卡管「cue 文本怎么被索引」，正交。
- 本卡验收走合成题库＋现有红测，不依赖 rules-v2 内容，不存在「验收被 #123 进度卡住」。
- 唯一残留耦合：#123 若产出显著更长/更偏的 cue 分布，1.95× 体积估算与 23/25 基线需要重新锚定——但那是 P6 的职责，且本卡验收是相对口径（同批探针上 bigram vs trigram），不构成本卡返工。**风险接受。**

### 3.2 对 P6：排序论证成立，但一处可放松

charter 的核心论证正确：trigram 上评 S2/S3 换述层会被结构性误伤（2 字词在索引里不存在），bigram 先落地 P6 的评测前提才公平。**但「P6 正式出题在本卡合并之后」偏保守**：

- **金标出题（人工写题、建诱饵、holdout 切分）与索引几何无关**，随时可做；
- 只有**评测跑分**必须在 bigram 落地后才有公平前提。

建议把 §4 的表述改为「P6 出题可与本卡并行、正式出分在本卡合并之后」，可缩短关键路径（出题是人力长周期项）。此项为主控取舍项：若担心出题者被当前召回缺陷带偏措辞，维持原状也可接受，但须二选一记录理由。**非阻塞。**

### 3.3 真正的时序红线：部署切换（并入 Q1 条件①）

编码、红测、合并都可以在真机授权之前完成；**真机生效必须与授权重建原子切换**（见 §1.2 条件①）。建议把这条写进 §4 时序表，显式排除「合并即上线」的默认假设。拆句工（本卡合并＋P6 达标后立项）的依赖陈述无异议。

## 4. 三问之外的全稿一致性扫描（补充发现）

1. **【红线·预期管理】合并后真人整句召回预期仍为 0/16**（E-8：整句 B1 0/16；碎片枚举 B2′ 才 16/16）。本卡的用户可感收益是短词可查（oracle 9/25→≥23/25），**不是**端到端召回修复。§6 验收应加一行：「合并后真人整句召回预期不变（仍 0/16），收益口径为 oracle 短词 ≥23/25」；§9 签认栏建议加一项「预期管理已对齐」。——这是本轮外审最需要主控看见的一句话。
2. **【变异反证补一条】** §5 变异清单缺「去掉查询 phrase 包裹」。去掉后无序 bigram 可命中，应恰好打红红测 3（3/4 字专名滑窗命中且不误撞含首片的异卡）。四点变五点。
3. **【红测自身防 flaky】** §5-2「同查询两次 MATCH 计划相等」中的查询计划受 SQLite 统计信息影响、非严格稳定；建议断言收窄为「结果集与顺序两次相等」，计划比对降级为诊断信息，防红测自身变成不稳定源。
4. **【验收微调】** §6 误召观察上限现在引用的是 B2′ 基线（2 例，属拆句工口径）。本卡口径下（整句 B1、短语复核）误召基线应单独定义——建议直接写「本卡口径下误召 0 容忍（原文复核兜底），B2′ 误召 2 例为拆句工观察起点」。
5. **【流程项】** 挂账②（#123 台账 11.4.0 追认）是取号前置，建议在 §9 签认栏 checklist 单列一格，防取号时遗漏。
