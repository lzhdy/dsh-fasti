## 1. 项目背景：这是一个什么系统

### 1.1 一句话

FasTI 插件（代号「历」）是一个运行在桌面端 LLM 宿主（基于 cordis/dsh-llm 的聊天应用）内的**个人连续记忆插件**：它把"她"（用户本人）与宿主的全部对话与感知，沉淀为不可篡改的原始日志、可重建的检索投影、以及可供对话时检索的"记忆卡"，目标是让模型在长期使用中保持一个连续、可解释、可审计的"她"，而不是一个每次重启都失忆的聊天机器人。

### 1.2 五块功能地图（全项目只分这五块，不新增第六块）

| 块 | 职责 | 与本任务关系 |
|---|---|---|
| A 块 | 真源与契约：append-only 不可变日志、类型契约、原子文件写、SQLite 投影基建 | #42 只消费 A 块真源，绝不回写 |
| B 块 | 记忆机制：闭合摘要、记忆卡、检索门、复盘/做梦/遗忘等判断类产线 | **#42 是 B 块核心卡** |
| C 块 | 主动性：主动发起交流等行动（"发消息/打开网页"等能力不算 C，归 D） | #42 不依赖 C |
| D 块 | 能力与外设：发消息、语音、浏览器、摄像头/麦克风等适配器，含权限、审计、回滚、刹车 | #42 不依赖 D |
| E 块 | 身份连续性：跨块的自我模型，横切所有块，最后建设 | #42 不依赖 E |

### 1.3 当前建设阶段

- A 块真源与 L1 基础投影已上线并经多轮验收；B 块记忆层 v1 以**离线脚手架**形态建成：记忆卡目前只能由人工在命令行跑离线构建器全量重建，运行期（她正在聊天的实时过程中）不会产生任何新卡。
- 任务 #114（拆除运行期绕门支路）、#115（检索落空时的自主回查通道，含两个宿主工具）刚刚验收交付，测试基线 873 个用例全绿、TypeScript 双工程零错误。
- 2026-11-15 主控决定**空白重启**：真实数据根已整体冷备后清零，系统从完全空白的她重新开始。历史上一批旧契约产生的"语义标签悬空锚点"（34 个）随清零物理离开活动库，#42 不再承担存量数据修复义务，只需面向未来的干净数据设计。
- #42 是当前排期的瓶颈卡：#90（锚点写入闸）、#43/#116（记忆窗口注入）、#94（复盘产线）四条线都在等它。

## 2. 术语与数据模型（评审前必须先建立的心智模型）

### 2.1 四层数据

```
原始轮次 raw-turns（L0 真源，append-only JSONL）
   │  纯机械转换，不调 LLM、不改一个字
   ▼
经历 experiences（结构层真源，append-only JSONL，每条有 26 位 ULID）
   │  事件分段器按字数/会话边界切成"事件"，异步闭合时摘要 LLM 产出摘要与锚点
   ▼
事件 events（二级真源，append-only JSONL，只追加版本，永不原地改/删）
   │  离线/运行期构建器消费"已闭合且摘要达标"的事件版本
   ▼
记忆索引 projection/memory-index/（可整体删除重建的 SQLite 投影 + JSONL 台账）
   ├── memory-index.sqlite：记忆卡、别名、FTS 全文索引、miss 观测等表
   ├── decisions.jsonl：决策台账（每次建卡/改别名/失效都留痕）
   └── revisions.jsonl：修订链（链式校验，防投影被偷偷篡改）
```

关键定性：

- **真源（前三层 JSONL）是日记**：append-only、不可变、冻结面禁能力清单里没有 update/delete 原语。任何新代码都只能追加，不能改历史。
- **投影（memory-index）是书后的索引卡片盒**：不是真源，允许随时整体删除、照真源重建。#42 的全部写操作只能落在投影，一个字节都不许进真源。
- 物理上真源按通道命名空间分目录（当前只有 `dsh` 通道；`scene.channel` 是开放枚举，未来含 qq/browser/camera），新增通道不需要改目录级逻辑。

### 2.2 anchors（锚点）

事件闭合时，摘要流程给事件挂一组 `anchors`：**设计本意**是该事件引用的经历 ULID 列表（26 位 Crockford Base32），记忆卡通过锚点回指具体经历。

历史教训：契约一期 anchors"生成但不消费"，只校验字符串数组形状，摘要 LLM 曾自由生成"煮冻饺子""web_search"这类语义标签；记忆构建器是第一个真正消费 anchors 的组件，它要求每个锚点都能在经历全集里查到对应 ULID，查不到就抛 `MemoryAnchorDanglingError`、零产物（fail-fast，不允许糊出指错地方的卡）。未来的 #90 写入闸会在写入侧分三层拦住新脏数据（L1 单记录 ULID 形态闸、L2 闭合慢路径同通道时间窗候选池引用完整性闸、L3 摘要端候选序号反幻觉），但 #90 尚未建设。

### 2.3 记忆卡（MemoryCard）与两类字段

记忆卡是检索的基本单元，字段分两类，这个区分是 #42 范围切分的核心：

1. **结构化/确定性字段**：`card_id`、`anchor_json`（锚点集合）、channel、时间窗、初始 weight/hit_count（恒 0）、失效时间戳（NULL）等。它们由构建器从真源按**确定性公式**派生，重放幂等，双跑逐行相等，天然不需要人、也不需要 LLM。
2. **自然语言检索词字段**：displayCues（展示提示词）、aliases（检索别名）、discriminator（区分语）、sensitive 标记。它们决定"她用什么人话能搜到这张卡"。历史上这部分只能人工标注，因为有两条红线：
   - **H7 子串反查禁止**：不许把事件摘要整句抄进卡（否则检索退化为子串匹配，索引失去意义）；
   - **K5 禁止 LLM 静默改写已存事实**：模型不能自己给自己写"记忆"，任何模型产出的检索词都必须有显式决策留痕与数据考核出口。

### 2.4 决策台账 DecisionRecord（投影内，不是真源）

每次投影变更都追加一条决策记录，当前 TypeScript 结构（`src/memory/types.ts`）：

```ts
interface DecisionRecord {
  decision_id: string;            // ULID
  at_ms: number;
  action: 'create-card' | 'update-cues' | 'tombstone-card' | 'add-alias' | 'invalidate';
  card_id: string | null;
  event_id: string;
  anchor_json: string;            // 经历 id 列表
  content_hash: string;           // 决策时锚点快照哈希
  model_tag: string;              // 决策规则/模型标识 + prompt 版本
  reason: string;                 // 理由码+一句话，不复制原文
  created_by: 'her';              // 联合类型目前只有这一个合法值
}
```

注意 `created_by` 联合类型**只有 `'her'`**：人工种子通道（`seed.ts`、人工 remap）已于 2026-11-12 整体删除，运行期沉淀的唯一合法主体是"她"，不存在人写卡、机器替她拍板的入口。`operator` 等旧枚举也已收窄，离线构建器唯一操作人标识是 `'offline-cli'`，规则版本标识 `'rules-v1'`。

### 2.5 影子模式（shadow）与检索落空（miss）

- 记忆门有三态：off（不接）、shadow（只观测不影响回答）、on（真正注入）。当前 #115 能力在 off/shadow 可验，on 态生产写要等 #90/#91。
- #115 刚交付的 miss 通道：检索落空时经窄柄 `recordMiss` 同步写一行观测、经 `addMissAlias` 走显式别名决策；这些只写投影，且锚点字段当前恒 null（等 #116 窗口接线回填）。

## 3. 硬约束（评审方案的笼子，违反即淘汰）

### 3.1 架构冻结项（K 系列，节录与本任务相关者）

- **K1**：不引入向量/embedding 检索；**K2**：不引图库。检索只允许确定性的 BM25/FTS/别名精确匹配等可解释机制，分数构成必须可解释（scoreParts 可审计）。
- **K3**：内核**无常驻定时器/cron/守护进程**。所有周期性工作由宿主（外部）后台 worker 驱动，内核只暴露"可被调用一次的 drain 能力"。
- **K5**：禁止 LLM 静默生成/改写已存事实卡。唯一合法方向是"经她的决策留痕生成新决策行"；任何检索词自动化都要有可复算数据指标与外审解冻流程。
- **K7**：记忆契约无情绪/心情/重要度字段，客观第三人称，不注入人格。
- **K8**：LLM 判定不进对话摄入热路径；热路径只做内存入队，不 await 不写盘。
- **K9**：禁止概念空铺——不留空接口、空表、占位抽象；每个新投影/新阶段独立立项、配验收与重建协议。
- **source-append-only**：真源只追加；**projection-rebuildable**：投影必须可整体丢弃并从真源重建。
- 不新增生产依赖；不实现 erase（删除闭包是另一张卡 #95 的命题，本期不做）。

### 3.2 单写者与失败纪律

- 所有真源写经单写者 `WriterQueue`（`src/source/writer-queue.ts`）串行化，原子落盘走 tmp+rename。
- 闭合慢路径既有失败纪律：LLM/写盘失败按一次失败处理、退避重试，连续失败标 permanent 并让事件保持 pending，**不许写半份坏版本、不许用占位数据糊过去**。
- 运行期窄柄已有只读降级：当投影被离线构建任务占用（写锁不可得）时，`requireWriter()` 抛 `UnavailableError('记忆索引正被离线任务占用，运行期窄柄已降级只读')`，读能力不受影响。

## 4. 现状代码盘点（#42 开工时的地基）

### 4.1 离线记忆构建器 `src/memory/builder.ts`（446 行）

全量重建入口，主流程分段：冻结接口声明 → 确定性派生公式 → 旧库快照（只读）→ 决策回放 → 构建主流程。关键行为：

1. 读真源，经 `foldCurrentEvents` 折叠事件版本到当前态，只收 `status==='closed' && summary_quality==='ready'` 的事件（约 254 行）；
2. 步骤 4 悬空硬失败：每个 anchor 必须 `isUlid()` 形态合法且存在于经历全集，否则 `MemoryAnchorDanglingError`、零产物（约 269 行）；
3. 确定性派生卡 id 与结构化字段，零正文纪律（不把事件正文抄进卡）；
4. 经 `store.transactionApply(changes, revision, decisions)` 原子应用：卡/别名表与 FTS 同步、revisions 链追加、decisions.jsonl 台账追加；双跑幂等、逐行相等。

配套：`src/memory/serial.ts` 候选序号化反幻觉协议（模型只能回候选序号，未知序号拒绝并允许一次重取，禁止猜序号）；`src/memory/audit/` 离线考核 harness（R1/R2/R3 指标、DRM 诱饵、provenance 100% 硬失败）。

### 4.2 运行期窄柄 `src/memory/runtime.ts`

`openMemoryRuntime(paths)` 返回的 `RuntimeMemoryHandle` 当前**恰好六个方法**，面非常窄：

| 方法 | 能力 |
|---|---|
| `searchExplained(query)` | 带分数解释的只读检索 |
| `getCardsByAnchor(experienceId)` | 按锚点只读查卡 |
| `addMissAlias(input)` | 落空别名决策（写，需写锁） |
| `recordMiss(input)` | 落空观测单行登记（写，需写锁） |
| `recordShadowObservation(input)` | 影子观测登记（写，需写锁） |
| `close()` | 释放 |

写方法统一经 `requireWriter()`：离线任务持锁时整个窄柄确定性降级为只读。窄柄里**没有**任何建卡/派生/决策面：`transactionApply`、`appendDecision` 目前只有离线构建器一个生产调用方。

### 4.3 宿主 worker 与 drain 模式（#42 要复用的挂载范式）

- 摄入热路径只把原始轮次入内存队列即返回；事件闭合后的摘要慢路径由宿主后台 worker 一轮轮驱动：适配层 `src/adapters/dsh/llm.ts` 内有 `drain()` 循环（约 145 行），调门面 `Fasti.drainClosure(maxPerRound, maxDurationMs)`（`src/api/index.ts` 约 650 行），每轮有条数与时长预算、返回处理条数（0 表示队列空、worker 歇一拍），插件关闭后直接返回 0。
- 内核自己不持有任何定时器；worker 存活于宿主适配层。
- 这就是立项书为 #42 指定的合法挂载范式：**新增一个与 closure drain 同构的"记忆投影 drain"**，在事件进入 closed+ready 后异步增量构建投影，不进热路径、不新建调度器、只写可重建投影。

### 4.4 装配层 `src/assembly/`

宿主工具与记忆窄柄的接线层：`memory-tools.ts` 定义宿主可见工具、`host-tool-runtime.ts` 做信封/白名单/形状闸（#115 刚加固为 fail-closed 两层校验）、`source-lookup.ts` 是只读检索端口、`index.ts` 负责依赖注入。装配层是 M6 门唯一白名单例外，天然是"记忆投影 drain"接线的候选位置。

### 4.5 事件侧"她的判断"入口

`src/event/closure.ts`（闭合，含摘要慢路径与版本追加）、`src/event/correction.ts`（她发起的修正/重写，会追加事件新版本、刷新话题线与锚点）。事件版本天然带 `created_by` 溯源，她本人的判断是以"追加事件版本"的形式留在真源里的，而不是存在某个运行期命令通道。

## 5. #42 的目标、拟分批与明确不做

### 5.1 目标

正常使用阶段，记忆沉淀与检索**运行回路零人工**：不需要人逐条审批建卡，也不设"机器起草、人点确认"常驻审核岗。人的合法位置只在工程期（定规则、标一次性金标、按数据外审解冻冻结项）。具体交付：closed+ready 事件出现后，宿主 worker 经新增 drain 入口驱动记忆层，用离线构建器同一套确定性派生规则增量产出记忆卡并落 decisions/revisions 台账，全程幂等、只写投影、失败有确定姿态。

### 5.2 拟分四批（每批独立 TDD、独立评审，评审者可挑战切法）

- **B0 依赖门设计（本轮只出设计不写码）**：确定 drain 入口归属与 M6 门修订形态，更新静态门白名单与投毒用例。
- **B1 投影 drain 接线**：仿 drainClosure 的预算化 drain；只写投影；离线构建持锁时只读降级、本轮跳过不报错；增量状态从何而来（候选：投影 revisions 水位/事件版本游标，全部可重建，禁止发明不可重建的隐藏状态）。
- **B2 结构化字段运行期自动建卡**：复用 builder 确定性派生与悬空硬失败纪律，经 `transactionApply` 落卡与台账，幂等双跑逐行相等；处理"事件新版本使旧卡过时"的失效/重算（invalidate/tombstone 语义已在 action 枚举里）。
- **B3 她的判断运行期入口**：她在闭合/修正事件版本里留下的判断如何被 drain 回放成决策行（例如 add-alias、invalidate），不开任何模型可直写的决策工具。

### 5.3 明确不做（请评审者不要建议这些方向）

1. 自然语言 cue/alias/discriminator 的运行期自动化：列为待数据裁决的假设。两条候选路线（零模型确定性抽词；受约束模型只能序号选择＋离线 R1≥0.85/R2≤0.05 考核＋bootstrap 置信区间＋外审解冻）本期都不选、不实现，当前样本量（空白重启后从零积累）统计上不足以下结论。
2. erase/真删除、定时器/守护进程、任何真源写、情绪数值、重要度评分、向量库、图库、常驻 AI 审核岗。
3. 历史数据迁移/补救（空白重启后无此对象）。
4. 多设备/同步/服务端。

## 6. 典型运行时序（目标态，供评审者校验理解）

1. 她与宿主对话，原始轮次入队即返回（热路径零 IO 等待）。
2. 宿主 worker 心跳调 `drainClosure`：事件达闭合条件 → 慢路径调摘要 LLM → 产出摘要、话题线、anchors（#90 建成前 anchors 仍可能是自由文本，见问题 7）→ 追加事件版本到 events 真源，事件 closed+ready。
3. 同一个 worker（或并列的同构 drain）调**新增的记忆投影 drain**：读取自上次水位以来的新 closed+ready 版本，跑确定性派生；写锁不可得就只读跳过等下一轮。
4. 经窄柄/事务原语把卡变更、revisions、decisions（created_by='her'、model_tag='rules-v1' 等规则标识）原子写入投影；任何不确定的自然语言字段一律留空/走既有 abstain 语义，不调 LLM 补。
5. 她事后修正事件 → 新事件版本 → 下一轮 drain 检测到锚点快照变化 → 确定性失效/重建受影响卡，台账留痕。
6. 对话侧检索仍走 #115 的只读端口与 miss 通道，路径不变。

## 7. 主要风险与已识别失败模式

- **R-a 依赖环/热路径污染**：drain 接线若放错层，可能让 api/event 直接依赖 memory，破坏 M6 门与 K8，且记忆库慢查询拖垮对话。
- **R-b 双写竞争**：离线全量构建与运行期增量 drain 并发写同一投影（当前靠写锁只读降级缓解，需验证跳过/重放的幂等完备性）。
- **R-c 增量状态丢失或漂移**：水位若设计成不可重建的私有状态，违背 projection-rebuildable；崩溃在半轮中间必须能无损重放。
- **R-d 事件新版本/修正导致卡片过期**：增量建卡不能只处理"新增"，还要确定性处理"旧卡失效"，否则投影与真源逐渐不一致。
- **R-e 脏锚点复发**：#90 未建时新 anchors 无写入侧保证，drain 会遇到悬空锚点；姿态需要预先定义（硬失败跳过？事件挂 pending？不能静默建坏卡）。
- **R-f 台账失真**：决策行必须能解释每张卡为什么存在；任何跳过/失败都要有可观测记录，不能"悄悄没建"。
- **R-g 范围蠕变**：评审过程中最容易被塞进来的是检索词 LLM 自动化、重要度打分、定时复盘调度，全部属本期红线。
- **R-h 测试沙箱与真机偏差**：当前全部离线合成测试，真机 T17 未验收；drain 在宿主 worker 里的实际节拍、关停时序只能在隔离 DSH_HOME 真机验收中覆盖。

## 8. 七个待裁决问题（请逐条给出明确意见与理由）

### 问题 1：#42 与 #90（锚点写入闸）的先后顺序

- 背景：内部排期表登记 #90 依赖 #42（#42 先行）；而旧立项书 §4 主张写入闸 P2 先行、增量锚点洁净后再做自动建卡，理由是"垃圾进垃圾出"。
- 我方倾向：**#42 先行**。理由：#42 的结构性部分（drain、确定性派生、台账）不依赖写入闸，builder 自带悬空硬失败可在 drain 期充当临时拦截；检索词自动化本来就后置；且 #42 一卡压四线。#90 紧随其后，在 on 态生产写之前闭环。
- 请回答：该倾向是否成立？若你主张 #90 先行，请给出 #42 四条下游线的替代排期；若同意 #42 先行，请给出 #90 落地前 drain 遇到脏锚点的具体处置姿态（与问题 3 联动）。

### 问题 2：M6 门往哪开、drain 入口长什么样

- 候选 A：在 `src/assembly/` 装配层新增 drain 编排（扩 ASSEMBLY_VALUE_ALLOWLIST 白名单枚举新符号，补投毒用例），`src/api` 门面新增一个被 worker 调用的 `drainMemoryProjection` 方法，但 api 内核不直接 import memory，由装配层把 memory 纯函数注入门面（与现有依赖注入风格一致）。
- 候选 B：在宿主适配层 `src/adapters/dsh/` 直接持有 memory 构建函数（仍在规则①实时目录内，需要为 adapters 开新例外，门的形状更复杂）。
- 候选 C：给运行期窄柄 `RuntimeMemoryHandle` 加第七个方法（如 `applyReadyEvent`），把构建能力收进 memory 内部，装配层只调窄柄。
- 我方倾向：**A 或 C，明确反对 B**；初步更偏向 A（门面保持对 worker 的统一 drain 面，窄柄维持"检索+miss"的小面，构建编排留在装配层）。
- 请回答：三个候选的优劣与你推荐的依赖方向；若选 A，门面方法与 assembly 编排的职责切分怎么划；白名单应枚举哪些符号；需要新增哪些投毒探针。

### 问题 3：drain 失败与悬空锚点的姿态

- 背景：闭合慢路径纪律是失败退避、permanent 后保持 pending；窄柄已有持锁只读降级。
- 开放点：自动建卡某轮失败（锁竞争、悬空锚点、数据暂时不完整）时，是静默跳过等下轮重建即可，还是需要显式的故障观测/维修通道（不是常驻审核岗，是 K11 意义上的坏了能修）？空 anchors 的 closed+ready 事件算合法（"暂无可引用经历"）还是不合格？
- 请回答：失败分级表（哪些可静默重试、哪些必须 permanent 并留观测）、空 anchors 的口径建议、需要在投影里新增什么可观测结构（注意 K9，不许先建空表）。

### 问题 4："她的判断"怎么进 decisions 台账才不会被模型冒充

- 背景：DecisionRecord.created_by 只有 'her'；模型侧只能通过宿主工具接触窄柄，当前工具面没有决策写入。
- 候选：(a) 只允许 drain 从事件版本（closure/correction 留痕）回放生成决策行，永不暴露模型直写工具；(b) 新增一个带强校验的宿主工具，模型只能提交"申请"、由确定性规则裁决后留痕。
- 我方倾向 (a)，认为 (b) 容易演变成机器替她决定。
- 请回答：选哪个、为什么；若选 (a)，correction 事件版本到 add-alias/invalidate 决策行的确定性映射规则应该怎么设计才幂等且可审计。

### 问题 5：增量水位与重建协议

- 请回答：增量 drain 的进度状态应该存在哪、长什么样（要求可随投影整体删除重建、崩溃可重放）；如何证明增量投影与离线全量构建结果逐行相等（等数替换/双跑对账的具体测试设计）；事件新版本导致旧卡失效的重算边界怎么定。

### 问题 6：检索词自动化的长期路线（本期只做纸面评估，不写码）

- 请回答：零模型确定性抽词与受约束模型候选＋离线门禁两条路线各自的天花板与风险；R1≥0.85/R2≤0.05 这套指标定义是否充分、还缺什么指标（如检索漏报率、漂移监控）；在"零人工运行回路"前提下，外审解冻的触发与回滚机制怎么设计才不变成事实上的常驻人工岗。

### 问题 7：#90 落地前的过渡防污

- 背景：空白重启后从零积累数据，而 L1/L2/L3 写入闸尚未建设，自由文本 anchors 可能复发；builder/drain 的悬空硬失败是仅有的拦截。
- 请回答：在不提前实现 #90、不违反 K9 的前提下，过渡期还能采取哪些零成本或低成本防护（例如 shadow 期 anchors 质量观测表、drain 失败率阈值告警）；这些防护如何在 #90 落地后无损拆除或转正。
