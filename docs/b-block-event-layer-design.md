## 0. 一句话总览

**记录本存流水（一条一条，带时间点）；阶段 0 先把工具轮类型化（工具轮不再冒充对话），切分员用机械信号直接闭合、语义信号只标候选，把流水聚成事件（一件一件，带时间范围）；一闭合就先置 `closed`，后台一次 LLM 生成客观摘要、提取锚点、给出非权威话题转折候选，并用原始记录 embedding 投票产生候选、由 LLM 判定它挂到哪条网状话题线上；记事本存事件，筛选员只贴中性机械标签；复盘时她消化并写进记忆本。事件是二级真源——写进去就不许算法重算，只许她修正。**

## 1. 三层命名与职责（必须先定，否则实现方必乱）

| 层 | 用户说法 | 里面是什么 | 粒度 | 时间形态 | 现状 |
|---|---|---|---|---|---|
| 第一层 | **记录本** | 一条一条的流水：谁 几点 在哪 说了什么 / 做了什么 / 用了什么工具 / 上了哪个网页 / 看了什么 | 一条消息、一次动作 | 单点时刻 | **已有**，即代码里的 `experiences`（247 条），需补类型 |
| 第二层 | **记事本** | 一件一件的事：一段对话、一次浏览、一次一起做的事 | 一个事件 | 时间范围 `[start, end]` | **新建** |
| 第三层 | **记忆本** | 她真正记住的：事实、对关系的理解、自我认知、三观、倾向 | 一条记忆 / 一条人格主条目 | 无固定形态 | 旧系统有，B 块接新地基 |

**两个加工角色**：事件切分员（流水 → 事件）、筛选员（事件 → 中性标签）。**一次消化**：复盘。

### 1.1 命名冲突的处置（重要）

旧骨架里"记事本升级成 MP4（存指针不存像素）"指的是**记忆单元**。按新流程，媒体能力应挂在**记录本**——因为只有原始记录才承载字节引用，事件块只存指向记录本的指针。

**处置**：`记事本` = 事件层（本稿）；`记忆本` = 沉淀层；媒体引用能力绑在 `记录本`，向上逐层只透传指针。

## 2. 为什么必须切事件（问题陈述）

现在 247 条记录 = 247 条消息，一条 user 一条 assistant 各算一块。按这个粒度复盘，会出三个问题：

1. **碎**：一次 20 句的对话被切成 20 个"经历"，复盘要自己在脑子里拼上下文；
2. **错位**：user 那条和 assistant 那条被当成两件事，而它们本来是同一件事的两半；
3. **无法回答"发生了什么"**：记录本能回答"第 42 条说了什么"，回答不了"那天我们聊了什么"。

事件层就是为了把"流水"熬成"事"。用户 2026-11-09 明确：**"整个程序都是在一段一段经历上进行的"**——事件是复盘、筛选、做梦、回忆的公共输入单位。

## 3. 事件是什么

### 3.1 定义

一个事件 = 记录本里**连续的一段**，满足：它讲的是同一件可命名的事。

### 3.2 事件字段（对应 27 条第 14 条）

| 字段 | 含义 | 何时产生 |
|---|---|---|
| `id` | 事件 ULID；多版本共享同一 id | 创建时 |
| `version` | 版本号；每次状态/边界推进追加一行（版本保留规则见 D4） | 维护 |
| `channel` | 所属通道（事件按通道隔离，§3.4） | 创建时 |
| `summary` | 一句话摘要，**客观语气、第三人称、不带评价**；后台未完成时为 `null` | **闭合后异步生成**（§6.1） |
| `key_points` | 关键点 / 关键数据（数组，可空） | 同上 |
| `pointers` | 原文指针组：指向记录本的具体条目 | 边界确定时（必需，闭合即可得） |
| `status` | 状态机（§3.4） | 维护 |
| `closed_reason` | 闭合的机械原因（封闭枚举，写模式校验；`null` = 未机械闭合） | 闭合时 |
| `effective_chars` | 有效对话字数累计（**可空**：`null` = 旧数据/未统计；restore 直接读它，不从 pointers 重算） | 摄入时增量维护 |
| `boundary_candidates` | 非权威候选标记（含慢路径"话题跳转"与机械孤立标注；不改 pointers/status） | 见 §5.2 / §6.4 |
| `time_range` | `[started_at, ended_at]`，允许为零长度 | 边界确定时 |
| `assembled_at` | 被切成事件的时刻（与 `time_range` 是两条轴） | 边界确定时 |
| `anchors` | 事件锚点：具体动作 / 事实进展 / 计划（数组），用于话题线判定（§5.5） | 后台与摘要同一次调用 |
| `topic_lines` | 所属话题线 id 列表（**网状，可多条、未判定前为空**），见 §3.5 | 后台 LLM 判定 |
| `summary_quality` | `pending`（后台处理中）/ `ready`（已生成）；**不设 template——降级就是保持 null + pending，不伪造占位文案**（§6.3） | 维护 |
| `summary_source` | 当前摘要由谁写：`llm`（后台生成）/ `her`（她手写）；决定重跑时能不能覆盖（§7.2） | 随摘要产生 |
| `summary_prompt_version` | 生成该摘要时的提示词版本号（字符串，**可空**：她手写或未生成时为 `null`） | 后台摘要落盘时 |
| `summary_model` | 生成该摘要的模型标识（字符串，**可空**） | 后台摘要落盘时 |

> 另：记录本（Experience）侧在阶段 0 新增加法字段 **`char_count`**（number：对话轮记 raw_text 码点长度，工具轮记 0），作为 `effective_chars` 的逐记录来源；契约层无 `speaker` 字段，工具轮判定用 `action`/`outcome` 与原文层复核，不直接引用宿主 speaker。

> `summary_prompt_version` / `summary_model` **只做溯源，不做评分**（不是质量分、不参与任何排序）。加它们的唯一目的是：将来换模型/改 prompt 后重跑同一事件时，能分辨"这条摘要是在哪个版本下产生的"，而不是把不同版本的输出混在一起比较（v1.1 补）。

> 骨架原写"重要性"为六要素之一。**本稿确认删掉**：真源层一旦带"重要性"就等于预设了什么重要（撞红线②）。她的判断落在复盘产物里，不落事件块字段。

### 3.3 时间形态（用户 2026-11-09 确认 + 三点补充）

- 记录本：一条一个**单点时刻**（已有 `occurred_at`）；
- 事件块：一个**时间范围**，允许 `start == end`（瞬时事件，如"她打开了一个网页"）；
- **双轴不混**：`time_range` 是"事何时发生"；`assembled_at` 是"何时被切成事件"；
- **不按日历切，按静默切**：聊到凌晨跨零点不因日期变化切成两个事件；但中间静默 ≥30 分钟就闭合。日历不是判据，静默才是（§5.5）。

### 3.4 状态机

```
open ──(静默/闭环)──→ closed ──(做梦/淘汰)──→ archived
  │                    │
  └──(她重开)───────────┘
                       └──(合并)──→ merged（带指向新事件的指针）
                       └──(拆分)──→ split（带指向子事件的指针）
```

- `open`：可能还有后续，回补原文时应并入；
- `closed`：已判定结束，正常复盘对象；
- `merged / split`：**被修正后的退役态**，自身不删，保留指向新事件的指针，供上层接力。

两条补充：

1. **闭合是即时的**：命中机械信号立即置 `closed`，**不等待 LLM**；摘要/锚点/挂线随后台异步补齐（§6.1），期间 `summary_quality: pending`。
2. **open 事件按通道隔离**：每个通道/来源各自维护一个 open 事件，不存在全局唯一 open；跨通道的连续性由话题线承担（§3.5）。
3. **通道切换时闭合谁（v0.6 点名，消除与 §5.2 的歧义）**：活动离开通道 A 转到通道 B 时，**闭合的是"被离开的 A"的 open 事件**，B 开（或续）自己的 open 事件；之后回到 A 是新事件，不会并回 A 已闭合的旧事件。于是"dsh → browser → dsh"自然得到三个事件（与 §5.5.1 一致），它们靠话题线连成一件事。

### 3.5 话题线（横向，网状）

事件块除了纵向的指针，还有一个**横向**归属：`topic_lines`。它把"同一件事在不同时间、不同通道里的多个片段"归到同一条线上。

**它是网状，不是单链**：一个事件可以同时属于多条话题线（比如"装修"和"和她的关系"两条线在同一件事上交汇）。

话题线是独立对象，最小结构：

```
TopicLine {
  id
  core_activity     核心活动是什么（一句话，由 LLM 写，随新事件可更新，更新留版本）
  event_ids[]       线上的事件，按时间排列
  status            active / closed
  version           版本号；线的修正留旧版（§7.5）
}
```

**线的上下文预算（防止长线喂爆 LLM）**：判定挂线时，喂给 LLM 的不是"线上全部事件全文"，而是 `core_activity` + **最近 10 个事件的锚点**（`recent_window=10`，可配置）；更早的事件只给 id 列表，让 LLM 知道线的长度但不读内容。无论线跑多长，输入恒定。

它与 §8 的"指针链"是**两回事**，务必分开命名，否则实现方必混：

| | 方向 | 连接什么 | 用途 |
|---|---|---|---|
| **指针链**（§8） | 纵向 | 记忆 → 事件 → 记录 → 资产 | 定位、取证、状态唯一真相 |
| **话题线**（本节） | 横向 | 事件 ↔ 事件（围绕同一核心活动） | 复盘/检索时把一件事的多个片段一起理解 |

话题线只在**横向**上成立：它不影响纵向的定位与状态，删掉话题线最多让复盘少一条线索，不会让取证失败。

**与旧 v0.3"接续指针"的差别**：旧设计是事件两两互指（previous/next），只能连成单链；新设计是事件挂到独立的话题线对象上，天然支持多线、分支与交叉，且 `core_activity` 让"这条线到底在讲什么"有明确答案。

**线本身也有修正操作**（并线/改挂线/关线/重开线），与事件修正同轨，见 §7.5。

## 4. 存储定位：二级真源（本稿最核心的一条）

| 候选 | 若按此做会怎样 | 结论 |
|---|---|---|
| 当投影 | 切分算法一升级就全量重算，**她改过的边界被抹掉** | 否 |
| 当一级真源 | 无意义——事件本身就是从流水派生的 | 否 |
| **当二级真源** | 派生自记录本，但**一旦写入即固化**；只允许她的修正与版本推进 | **采用** |

推论（写进实现纪律）：

1. 事件**不可由算法批量重建**；重建只允许"补齐缺失事件"（§7.4），不允许覆盖已有事件。
2. 事件必须**版本化**：每次边界修正留新版本；**保留/淘汰规则统一见 D4（默认不淘汰，超 20 版安全线才淘汰最老的纯算法版本，她的修正不淘汰）**，不再沿用旧的"固定 10 版"。
3. 事件层备份的重要性 = 真源级，不是索引级。

## 5. 切分判据

### 5.0 阶段 0：工具轮类型化（v1.3 新增，D12 落地）

#### 5.0.1 问题：工具轮一直在真源里，只是被错标成对话

实测（2026-11-09）：raw-turns 按 speaker 分布为 user 100 / assistant 113 / **tool 34**，工具轮字符占全部字符 **67.1%**（33181 / 49457）；而 experiences 247 条 `kind` 全部为 `dialogue`，带 `action`/`outcome` 的为 0。

工具调用的 `name`、`arguments`、结果正文本来就在 dsh 会话日志里，摄入侧（`src/api/index.ts` 唯一的 `kind:'dialogue'` 写入点）把它们一律写成对话。**缺的是类型化映射，不是宿主接口**——这更正了 v1.2 时期"任务闭环没有输入源"的判断。

#### 5.0.2 映射规则（纯加法，不改原文）

| raw-turn 形态 | 类型化产物 |
|---|---|
| assistant 轮中带工具调用步骤（name + arguments） | 该条 experience 补 `action: { type:'tool-call', tool, args }`（`args` 走原文指针，不内联）；`char_count=0` |
| speaker=tool 的结果轮（isError / content / error code） | 对应条补 `outcome: { status, error_type?, duration_ms?, tokens? }`，结果正文走指针；`char_count=0` |
| 普通 user/assistant 对话轮 | 维持 `kind='dialogue'`，不产生 action/outcome；`char_count` = 本条 raw_text 码点长度 |

约束：

1. 类型化只**补字段**，raw_text 与原文指针不动；阶段 0 对历史数据的补齐属于 §7.4 允许的"补齐"，不是"重建"；
2. 一次工具调用的**请求与结果拆在两条记录**，用 callId 关联（raw-turns 已带 callId），不强行合并成一条；
3. 映射不到未知工具形态时原样保留、不丢弃、不猜字段；
4. **原文层读取端口**：阶段 0 历史补齐时，除既有的 `readExperience` 外，注入与 raw-turns 并列的原文读取端口（按 event_id/seq 回查原始轮次），否则历史工具轮（只剩 `initiation:'environment'`）无法区分、"补齐"无输入。

#### 5.0.3 D12 契约（取值域已定；闭合判据待最终定案）

**取值域（已定，对齐 `src/contract/experience.ts` 已冻结的开放枚举）：**

| 契约项 | 取值 |

**"任务作用域"语义（钉死，替换"单次工具返回即完成"）：**

- 旧代码 `segmenter.ts:416-417` 的单记录判据（要求同条同时有 action 与 outcome）在"请求/结果拆两条"的映射下恒 false，须按本式替换。

### 5.2 两类信号：机械闭合 vs 语义候选（v0.5 修正，消除"到底切不切"的歧义）

信号分两类，**待遇不同，不能混为一谈**：

**A 类 · 机械闭合信号（命中即直接闭合，不需要语义判断）**

| 信号 | 阈值/用法 | 状态（v1.3 修订） | 依据 |
|---|---|---|---|
| **时间间隔** | 静默 ≥ **30 分钟**闭合当前事件；**由后台 worker 按时钟求值**（复用既有 5s 节拍，按 `now - 最后一条记录时刻 ≥30min` 补闭合并入队），不依赖下一条记录到达 | `active`（**时钟驱动**） | memv / gleanr 同值；现有实现只在摄入时判，属待修缺陷 |
| **有效对话字数上限** | 单事件有效对话（user/assistant 轮 raw_text，**排除工具轮**）≥ **7000 字**即机械闭合，写 `closed_reason='max-dialogue-chars'` | `active`（替代 v1.2 的 20 条硬上限，摄入驱动） | 7000/600=11.7:1 钉住压缩比；真实 8 段最大有效对话 5170 字，零影响 |
| **任务闭环** | 任务作用域结束时闭合（作用域级判据见 §5.0.3） | **`dormant`** —— 阶段 0 类型化与作用域判据落地后转 `active`；不是"自动"转，判据须先验证 | gleanr `close_on_tool_result`；本稿不采用"单次返回即闭合" |
| **硬保险丝** | 单事件原文（含工具 JSON）估算 ≥ **50k tokens** 即强制闭合，写 `closed_reason='max-chars'` | `active`（**仅兜底**） | 有效对话上限排除工具载荷，条数上限退役后需独立 raw 预算防炸；正常路径下有效对话上限一定先命中 |
| **场景切换** | 会话切换、通道切换（dsh → browser → camera）；**闭合被离开通道的 open 事件**（§3.4） | `active` | 旧稿 §5.1；ES-Mem 的 `TOPIC_SHIFT` 标签 |

> **"休眠"是显式状态，不是一句注释。** v1.3 下它的唤醒路径是：**阶段 0（§5.0）类型化 + 作用域级判据（§5.0.3）落地并经用例验证后，才把该信号从 `dormant` 改为 `active`**。休眠期间下游仍不许假设"事件边界可能落在任务完成处"：摘要提示词的"结果如何"保持条件句（§6.4）。
>
> **为什么用有效对话字数替换条数（v1.3 修订）**：实测工具轮占全库 67.1% 字符、但只占 14% 条数——按条数计数是在对机器载荷计数，这解释了"20 条 7 分钟就攒满、边界总落在 JSON 中间"。**有效对话字数只作为摘要压缩比的保守代理，不判信息量、不产生语义边界**；逐记录来源是阶段 0 的 `char_count`，事件行以 `effective_chars` 累计，restore 直接读该字段、不从 pointers 重算。
>
> **静默为什么必须时钟驱动（v1.3 修订）**：现有切分器是摄入驱动，静默靠下一条记录的时间差计算；用户离开后没有下一条，30 分钟规则永不求值，最后一个事件要等次日才闭合——即"记忆延迟一天"。复用后台 worker 既有 5 秒节拍（`startClosureWorker`，已在插件接线）补这个检查，零新定时器。**时钟检查独立于 LLM 端口注册**：事件闭合本身不需要模型，无端口时也应能闭合（摘要继续 pending 等端口恢复）。
>
> **硬保险丝的 token 估算**：不引 tokenizer、不增生产依赖，按 raw 字符数做保守换算（写进参数表，实现时固定一种换算）；两个 `max-*` 量纲不同（有效对话 vs 含工具 JSON 的原文），不可合并。


**B 类 · 语义候选信号（只标记"可能边界"，绝不自动切）**

**B 类 · 语义候选信号（只标记"可能边界"，绝不自动切）**

| 信号 | 用法 | 来源（v1.3 钉死） |
|---|---|---|
| **话题/意图突变** | 只标记候选，保留在当前事件内，闭合与否留给她在复盘时判断 | **唯一来源 = 慢路径摘要调用的附带输出**（`kind='话题跳转'`，§6.4）；不接 embedding 探测器（D11 留第二期） |

**关键纪律**：机械信号可以替她切（因为它们不涉及内容判断，只是时间/数量/场景的客观事实）；语义信号**绝不替她切**。宁可不切（事件偏大），不可乱切。

#### 5.2.1 量纲、驱动与优先级（审计收口）

1. **数据来源**：有效对话字数 = user/assistant 正文码点、排除工具轮；逐记录落 `char_count`（工具轮 0），事件行以可空 `effective_chars` 累计，restore 直接读、不从 pointers 重算。契约无 `speaker` 字段，工具轮判定用 `action`/`outcome` 与原文层复核。
2. **量纲决定驱动**：信息量类（有效对话字数、raw 预算）只在有新记录时增长 → 摄入驱动；时间/空隙类（静默 30min）必须在没有新记录时也能求值 → 时钟驱动。
3. **优先级**：通道切换 / 静默 / 任务闭环 > 硬保险丝 > 有效对话字数上限。先命中者写 `closed_reason`，一次只写一个，命中即 `return`。
4. **只闭合、不切边界**：闭合后立即进既有后台摘要队列；话题转折候选是同一次摘要调用的附带输出，只写 `boundary_candidates`，绝不改 `pointers`/`time_range`/`status`；她用 §7.1 拆分落地边界。
5. **修正权照旧**：上限闭合的事件与机械闭合事件同等对待；重开时 `closed_reason` 置 `null`。
6. **孤立记录**：`isPendingMergeOf` 的闭合原因集合取 `{silence, max-dialogue-chars, max-chars}`；`task-closure`/`channel-switch` 的单条不算孤条。

### 5.3 防误切（已核对五家做法）

1. 问候、客套、寒暄**不单独成事件**（并入相邻事件）；
2. **单条不孤立、但也不硬凑**：一条记录若前后都没有可并的，先挂"待归并"，**永不自动并入内容无关的事件**（v0.5 修正，见 D5）；它在复盘时可见，由她手动归并，或一直保持孤立；
3. 低置信**不切**；
4. 边界候选必须能被她的修正覆盖。

记录本：

  t2 her  "这里少了个括号"
  t3 user "改好了，谢谢"

### 5.5 跨时间段：切开，再用话题线接上

旧稿 §5.3 提过"跨会话同一件事接续"，v0.4 按 Membox（§15）的两段式机制重写。

#### 5.5.1 三种会遇到的形态

| 形态 | 例子 | 错误做法 | 本稿做法 |
|---|---|---|---|
| **跨天 / 长静默** | 昨晚聊装修聊到一半，今早接着说 | 合成一个事件，`time_range` 跨 12 小时、中间全空 | 两个独立事件，挂到同一条话题线 |
| **跨通道** | 在 dsh 里他说"我查一下"，然后她真的开了浏览器查，回来接着说结果 | 切成三个互不相关的事件，复盘时看不出是一件事 | 三个事件 + 同一条话题线，复盘时按线一起读 |
| **历史数据不连续** | 迁来的 247 条里，不同来源的相邻两条可能相隔几天 | 按"相邻就并入"硬凑 | 静默 ≥30 分钟即闭合，不因来源特殊 |

#### 5.5.2 为什么必须切开而不是合并

合并时间范围会带来三个失真：

1. **统计失真**：一个事件说"持续 12 小时"，实际只有前后各 10 分钟在人；
2. **检索失真**：按时间范围查"那天下午在干什么"，会捞出一个跨了两天的巨型事件；
3. **摘要失真**：600 字上限装不下两天的内容，必然写空话。

所以：**时间范围只装真实发生过交互的那一段；中间的空档不算进任何事件。**

#### 5.5.3 话题线怎么判定：原始记录 embedding 投票 + 一次 LLM 判定（v0.5 修正先后矛盾）

v0.4 曾写"用新锚点投票"，但锚点是 LLM 调用的输出，**不可能在同一次调用里先拿到自己还没生成的锚点去投票**。v0.5 把投票输入改为**闭合前就已存在的原始记录 embedding**，机械上成立，且不增加 LLM 调用。

**第一步 · 原始记录 embedding（闭合前就有，零额外成本）**

- 记录本每条条目的 embedding 在摄入时已算好（或从记录本向量里取）；
- 它是全量信息，比 LLM 提取的锚点召回更全（锚点可能漏，原始记录不会）。

**第二步 · 本地投票，只产生候选（在 LLM 调用之前完成）**

话题线本身不是向量，先明确**线侧表示**：每条 active 线维护一个向量，由它的 `core_activity` embedding 与成员事件的记录 embedding 聚合而成（对新记录取余弦的 max 或 top-k 平均，实现时定一种并固定）。

- 用新事件的原始记录 embedding，对每条 **active** 线的向量算余弦；
- 只保留余弦 ≥ **相似度下限**（`min_similarity`，可配置，初值取 0.7，待 D11 落地后按实测标定）的线，合并去重得到候选集；设下限是为了避免"宁多勿漏"退化成候选集恒非空；
- **closed 线不进候选集**；若要把新活动接回一条已关闭的线，属于她的操作（§7.5 增加 `reopenLine`），系统不自动复线；
- **embedding 不做最终决定**，只负责"把可能相关的线捞出来"。

**第三步 · 后台一次 LLM 调用，同时完成摘要与挂线判定**

输入：
- 候选线的 `core_activity` + 最近 10 个事件锚点（预算见 §3.5，更早只给 id）；
- 新事件的原始记录（或其压缩）；

LLM 在这一次调用里同时产出：
- `summary` / `key_points` / `anchors`；
- 挂线判定：新事件该挂到哪条候选线（或开新线），**一个事件可挂多条线**。

**LLM 的判据（核心：区分"话题相似"和"核心活动延续"）**：

| 挂线（任一成立） | 不挂线（任一成立） |
|---|---|
| 延续**同一核心活动**（不是相似话题） | 发起新的独立活动，即使话题相似 |
| 提供进展 / 结果 / 解决方案 / 直接后果 | 平行但独立的事件 |
| 逻辑或时间上的自然后继 | 没有具体进展的通用回应（"好的""嗯"） |
| 属于同一待办的下一步 | 只在表面词汇上相似 |

未被任何线接受的事件 → LLM 开新话题线。

**为什么这样不牺牲质量**：embedding 只负责召回（宁多勿漏），"该不该挂"这个语义判断完全在 LLM 手里；她在复盘时还可以再改。

#### 5.5.4 话题线的四条纪律

1. **不改写**：话题线归属一旦写入，后续事件合并/拆分时**不自动重连**，解析时顺线走（同 §7.3）；
2. **不闭环**：事件 → 话题线的归属必须是有向无环，发现成环即视为数据损坏，标记待她修；
3. **悬空留痕**：线上某个事件被删 → 标注"该事件已不可读"，话题线与其他事件保留，不连带删（同 §8.2）；
4. **核心活动可更新但留版本**：新事件让 `core_activity` 含义变化时，更新描述并留旧版，不静默覆盖。

#### 5.5.5 示例

```
话题线 L7  core_activity = "装修：从看风格到定方案"
  事件 E1  10-08 21:40 ~ 22:20  "聊装修风格，用户想先看北欧风案例"
  事件 E2  10-09 09:10 ~ 09:35  "她查了北欧风案例发给用户"
  事件 E3  10-09 20:05 ~ 20:40  "用户选定风格，决定下周约工长"
  L7.event_ids = [E1, E2, E3]

复盘读到 E1 时，话题线告诉它"这件事有后续 E2、E3"，三段一起理解，
但每个事件的 time_range 各自只装真实交互的那段。
```

## 6. 切分与摘要的执行路径（v0.2 的关键修正）

### 6.1 时间线（v0.5：即时闭合 + 异步后台，LLM 不进摄入热路径）

| 时机 | 做什么 | 调 LLM？ | 成本 |
|---|---|---|---|
| **摄入时（实时热路径）** | 记录本追加一条 → 并入该通道的 `open` 事件；命中**机械闭合信号**（§5.2 A 类）即**立即置 `closed`** 并开新事件；语义信号只标记 | **否** | 零 |
| **闭合后（后台队列，异步）** | ① 用原始记录 embedding 本地投票产生候选话题线；② **一次 LLM** 同时生成 `summary`/`key_points`/`anchors` 并判定挂线 | **是，一次** | 每事件一次 |
| **复盘时** | 她合并/拆分/改边界/重写摘要/改挂线 | 是（复盘本身） | 批次 |

**关键：闭合与 LLM 解耦。** 命中机械信号的瞬间状态就变成 `closed`，不等模型；后台处理期间事件已可正常检索（靠 pointers 回原文），`summary_quality: pending`。这保证 LLM 慢或挂掉都不会拖住对话——与"实时阶段零成本"一致。后台可把多个闭合事件攒批处理，但不改变"每事件一次 LLM"的语义。

#### 6.1.1 双流职责表（v1.1 补，实现期不许越界）

把上表固化成两条流的**职责边界**——不是"这里不调 LLM、那里调"的散落约定，而是架构级的两阶段：

| | **快路径（同步、零 LLM、零等待）** | **慢路径（异步、每事件一次 LLM）** |
|---|---|---|
| **写入** | 记录本追加一条；并入该通道 `open` 事件；机械闭合判定；写 `pointers` / `time_range` / `closed_reason`（含机械候选标记） | 只写**派生字段**：`summary` / `key_points` / `anchors` / `topic_lines` / `summary_quality` / `summary_prompt_version` / `summary_model`，**外加非权威 `boundary_candidates` 的"话题跳转"类（v1.3 扩）** |
| **绝不做什么** | 绝不调模型、绝不写 `summary` / `anchors`、绝不判定挂线 | **绝不改 `pointers`**、绝不改 `time_range`、绝不改 `status`（除了 `pending→ready` 这类派生位）；写 `boundary_candidates` 只产候选、不自动闭合、不移动记录 |
| **索引** | 记录 embedding 是否在摄入期算 → **D11 待定**；若定"摄入期算"才进快路径，否则下沉慢路径 | 事件摘要/锚点进检索索引（第二期） |

一句话纪律：**快路径只写"发生了什么"，慢路径只追加"我们认为它和什么相关"**。两边唯一的交汇点是"慢路径读快路径写的事实"，且只读不写。v1.3 允许慢路径写 `boundary_candidates` 是这条纪律的窄口子：话题跳转候选属于"我们认为哪里可能相关"，它不改变任何事实字段，权威边界仍只由她的修正（split/merge）落地。

### 6.2 为什么摘要不在实时生成（v0.1 的错误，已修正）

v0.1 曾写"实时模板拼接摘要"。**这条被否定**，理由：

1. 模板拼接就是定式判断——把"谁说了什么"机械套进句式，遇多轮交错、多话题、附件、工具调用就必然失真；
2. 业界的摘要**全部由 LLM 生成**，且**都在事件闭合后做**，没有在每条消息进来时生成的：
   - **Nemori**：episode 关闭时由 `Episode Generator` 生成"标题 + 第三人称叙事"；
   - **memv**：`EpisodeGenerator` 在 episode 形成时生成 Title + third-person narrative；
   - **gleanr**：episode 关闭触发 reflection，`background=True` 异步提取，不阻塞对话；
   - **ES-Mem**：Level-2 `Event Summaries` 由模型生成，且实测去掉摘要后单跳任务显著下降。
3. "闭合时一次"同时满足两件事：**质量**（LLM 写客观摘要）、**成本**（不是每轮，是每事件一次）。

### 6.3 降级

若后台没有可用模型（未配置 / 调用失败）：保持 `summary: null` + `summary_quality: "pending"`，事件照样可用（靠指针回原文）。后台按退避策略重试，**事后补齐**，不阻塞、不伪造占位文案；长期无法补齐时如实标注"摘要未生成"，不编造。

#### 6.3.1 后台的三条硬纪律（v1.1 补，全部来自已复现缺陷）

**纪律 1 · 每次模型调用必须有硬超时。**
超时时间可配置（建议默认 60 秒）；超时**按一次失败处理**（进失败明细、走既有退避），不得无限等待。
理由：一次挂死的调用不是"失败"，而是"没回来"——它不会进失败明细，却是**最静默的失效**：单队列串行处理时，它会永久停掉整条摘要队列，后续所有事件永远停在 `pending`，只能靠重启解开。断路器的前提是"知道它失败了"，挂死时连失败都不知道，所以**超时不能等断路器，必须先有**。

**纪律 2 · 单轮处理必须有上限。**
后台单轮同时受 **`maxPerRound=10`（批次条数预算）与 `maxDurationMs=120s`（时间预算）两个预算约束**，到任一限就返回、让调度器照常排下一轮；不得让一轮无限拉长。v1.3 退役的是事件切分的 20 条上限（`maxRecordsPerEvent`），**不是** `drainClosure` 的批次预算——两者是独立参数。

**纪律 3 · 结果过期必须丢弃。**
模型调用是异步的，期间事件可能被她修正（改边界 / 合并 / 拆分 / 重写摘要）。因此：
**写回派生字段前，必须比对"发起调用时的边界快照"（版本号 + pointers 的 id 序列）与当前态；不一致即丢弃本次结果——不写任何版本，事件保持 `pending`，重新入队等新边界。**
理由：否则会写出"按旧指针生成的摘要 + 新指针"的错配版本，且标成 `ready`；更糟的是它**不会自愈**——重跑任务已被同 id 去重吃掉，下一次扫描看到"已 `ready`"直接跳过，错误摘要永久留存。这正是"摘要必须覆盖其指针内容"这条不变式被打破的路径。
（这条对应事件溯源里的"版本失效丢弃"，但**不需要**把管线改造成完整的步骤日志：持久真相已经是 `summary_quality: pending` + 启动清道夫，"重放"语义已经有了，缺的只是这一道闸。）

### 6.4 摘要的写法约束与字数

**先定原则：字数只做纯技术兜底，不做语义判定；写多长由 LLM 按实际信息量决定。**

v0.3 曾按"记录条数"分档，问题是**条数不等于信息量**——20 条记录可能全是语气词、表情、无意义寒暄，按条数定字数必然注水。v0.4 取消分档：

**技术约束（只防空、防转录，不做语义/字数判定）**：

- **硬上限 600 字**：超过就是转录，不是摘要，拒绝；
- **不设硬下限，只查非空**：v0.5 取消原"15 字硬下限"——"她打开了一个网页"只有 8 个字，却是合格摘要；用字数卡下限，恰恰是用规则做语义检查（D9 想避免的）。是否"抓住了事"交给 LLM 自检和她复核，不用字数判断。

**写多长，交给生成摘要的 LLM**，prompt 里写清：

1. 语气词、表情、无意义寒暄（"嗯""哈哈""好的"）不进摘要；
2. 按实际信息量自然写，**能短则短**；
3. 应说清核心动作：**谁 / 做了什么 / 结果如何**（这是指引，不是硬规则检查项）。

**v1.2 补充约束（因"任务闭环休眠"而必须写死）**：三要素里的"结果如何"**必须写成条件句**——"若这段记录里有结果，说清结果；**没有结果就不要替它编一个结果**，写到什么程度就是什么程度即可"。原因：任务闭环信号在阶段 0 落地前处于休眠（§5.2），事件切口可能落在一件事的中间，此时"结果如何"会诱导模型给没有结果的事件补一个收尾结论——这正是"不伪造"要防的。摘要 prompt 的实际措辞与这条对齐，属于实现侧的必做项。

**v1.3 补充输出契约：同一次调用顺带产出话题转折候选。** 模型在生成摘要的同一次调用里，额外输出"本事件内部出现话题/意图转折的位置"，规则：

1. 模型只输出**输入序号**（它看到的编号），由适配器解析为 `at_pointer_id`；越界、重复、解析失败一律丢弃，候选数上限 5；
2. 候选只写进 `boundary_candidates`（`kind='话题跳转'`、`marked_at` 取系统时间），**非权威、不自动闭合、不改 pointers**；
3. 她在复盘界面看到候选后，用既有 split 落地边界；切错再用 merge 收回；第二期话题线负责把切开的片段重新接成一件事；
4. 单事件坏输出的错误半径只限本事件的非权威标记，不污染真源、不影响其他事件——这与"一次坏输出毁掉多个事件边界"的纯 LLM 方案有本质区别。

**写回路径（v1.3 审计补充，必须钉死）：**

- `LLMSummarizeResponse` 扩展候选字段（模型只输出序号，适配器解析），摘要 prompt 同步扩展，**`SUMMARY_PROMPT_VERSION` 必须 bump（v1 → v2）**——否则 `summary_prompt_version` 溯源成假信息；
- 候选必须随 `writeSummary` 的**同一次 `appendVersion`** 写回，共用 §6.3.1 纪律 3 的边界快照闸；`sameBoundary` 不通过时候选与摘要一起作废、不写任何版本；
- **不得另起写回路径**：模型在途期间她若改边界，分开写回会让按旧序号解析出的候选挂到新指针上，且绕过快照闸——这正是序号漂移的失效路径。

**三要素齐不齐，不写规则检查器**——规则判语义就是定式。两个出口：

1. 摘要本来就是 LLM 写的，让它在**同一次调用里输出前自检**，不另造检查器；
2. **她在复盘时是最终裁判**，觉得没抓住事就重写。

对照示例（同一个晚餐事件，注意区分"信息残缺"和"字数少"）：

```
✓ 合格（32 字）：用户问晚餐吃什么，她列了三个选项，用户说再想想。
✓ 合格（8 字）：她打开了一个网页。          ← 字数少但信息完整，不拦
✗ 注水（85 字）：用户在这个晚上提出了关于晚餐饮食选择方面的问题，
  希望得到一些有建设性的意见。针对这个问题，她进行了认真的思考……
✗ 信息残缺（4 字）：聊了晚餐。              ← 不是因为字数，是没说清谁做了什么
```

写法要求（三条）：

1. 第三人称、客观、只写发生了什么与关键数据；
2. **不写评价、不写她的感受、不写"重要"**（感受是复盘的事，见 27 条第 23 条）；
3. 单一事件内若有多个话题转折，按"先做什么、后做什么"顺叙，不展开对话细节。

## 7. 修正链路（一等能力，不是补丁）

### 7.1 五种事件修正

| 操作 | 语义 | 留痕 |
|---|---|---|
| 合并 | A + B → 新事件 C；A、B 置 `merged`，带 `merged_into: C` | 旧事件不删 |
| 拆分 | A → B1 + B2；A 置 `split`，带 `split_into: [B1,B2]` | 旧事件不删 |
| 改边界 | 把首/末 N 条记录挪出或挪入（即换 pointers） | 新版本 |
| 重开 | `closed → open` | 新版本 |
| 重写摘要 | 她手动改写 `summary`（`summary_source` 置 `her`） | 新版本，旧摘要留版本 |

#### 7.1.1 记录唯一归属（v1.1 补，硬不变式）

**一条记录同时只能属于一个事件。** 切分员是机械分区，每条记录落进唯一事件；这条不变式后续被整条链依赖——"摘要必须覆盖其全部指针内容"、孤立记录判定、待归并/跨通道标注、合并与拆分的分组校验，全都按"这条记录在哪个事件里"算。

因此**改边界不得跨事件"偷"记录**：

1. **移出**：只需从本事件 pointers 移除，记录随之"无事件覆盖"，回到孤儿候选池，等补切或她手动归并；
2. **移入**：移入的记录**必须当前不属于任何其它事件**。若已被别的当前态事件引用 → **拒绝本次移入**，并如实告诉她"该记录当前属于事件 X，请先在那里移出"；**不做自动换主**（自动从原事件移出会产生一次她没要求的修正，且原事件可能因此变空）。
3. 合并（A+B→C）时 C 的 pointers 取并集并按 id 去重（防御性，正常不应有交集）；拆分（A→B1+B2）的分组必须覆盖且仅覆盖 A 的 pointers。

**"属于"只算当前态里的未退役事件。** `merged` / `split` 的事件已把指针交给合并目标 / 子事件，若仍算归属，合并之后任何记录都无法再移入别的事件（永久假冲突）。`archived` 同理不计入归属——归档是"不再活跃"，不是"仍然占着记录"。（第一期不产生 `archived`，此条为语义预留。）

违反这条的后果不是"多一条指针"，而是**同一段原文被两个摘要各覆盖一次**，且此后每一次修正都在两处各写一版——而重建白名单会忠实地把污染保留下来，没有任何检测手段能发现它。

### 7.2 修正后派生字段怎么处理（v0.5 补闭环）

修正不只是换 pointers——`summary`/`anchors`/`topic_lines` 都是按旧 pointers 生成的，必须明确怎么办：

1. **派生字段必须重跑，不允许"换了指针却留旧摘要"**。否则"摘要必须覆盖其指针内容"这条隐含不变式就破了。
2. **她手写的摘要不被重跑覆盖（v0.6 优先级，P2-2）**：若当前版本 `summary_source: her`，重跑**只更新 anchors/topic_lines，不重新生成、不覆盖 summary**；要让摘要跟新边界走，得由她自己重写、或显式点"按新边界重生成"。重跑的 pending 窗口里，她的旧摘要照常展示并标注"摘要待更新（基于旧边界）"——这是她明确选择保留的，不算违反不变式。`summary_source: llm` 时重跑才正常生成新摘要。
3. **重跑走完整闭合管线**（后台 LLM，§6.1）：重跑期间 `summary_quality: pending`，新锚点/挂线（以及 llm 来源的新摘要）生成后写进**新版本**。
4. **新旧内容同时保留**：旧版本的 summary/anchors/topic_lines 完整留在版本历史里，可回退，不静默覆盖。
5. **合并/拆分产生的新事件（C、B1、B2）同样走完整闭合管线**：
   - 摘要由 LLM 重新生成，**不是拼接 A、B 的旧摘要**（拼接会重复、会漏）；
   - 挂线**重新判定**：把 A、B 原有的 topic_lines 作为"候选提示"喂给 LLM，但**不自动继承并集**——由 LLM 按新事件的实际内容决定，避免把旧错误一起继承。

### 7.3 上层指针的接力规则（v0.5 补 split 一对多）

**不自动改写记忆的指针**（那是她的东西，不能替她改）；解析时只读不写。

**合并（多对一，唯一目标）**：记忆指向 A，A 被合并成 C → 顺 `merged_into` 追到 C；注入时如实呈现"这条记忆来自一件后来被合并的事"。

**拆分（一对多，v0.6 补前提）**：纯链式里记忆只指向事件、本身不带记录指针，所以下表前 3 行**仅当记忆带记录级引用**（她锚定过原文引句、存了具体记录 id）时才可用；否则一律走第 4 行。也允许解析时用"记忆文本 vs 子事件摘要"做只读相似度提示，但提示不决定结果，最终仍呈现两个候选。

| 情形（需记忆带记录级引用） | 解析结果 |
|---|---|
| 记忆引用的记录落在 B1 | 解析到 B1 |
| 记忆引用的记录落在 B2 | 解析到 B2 |
| 引用的记录横跨 B1 和 B2 | **两个都呈现**，标注"来自一件后来被拆分的事" |
| 记忆无记录级引用、无法判断落点（默认情形） | 标"**已拆分**"，呈现 B1/B2 两个候选，**待她定**，不替她猜 |

### 7.4 允许"补齐"，不允许"重建"

- 允许：发现某段时间的记录没有任何事件覆盖 → 补切一段（幂等，按记录 id 去重）；
- 禁止：拿全量记录重跑切分算法去覆盖已有事件。

### 7.5 话题线的修正（v0.5 新增，P2-5）

线和事件一样会出错（并行通道可能同时开出两条讲同一件事的线），她需要能改。三种操作，**全部留版本、她专属、系统不自动执行**：

| 操作 | 语义 | 留痕 |
|---|---|---|
| 并线 `mergeLine` | L1 + L2 → 新线 L；L1、L2 置 `merged`，带 `merged_into: L` | 旧线不删，event_ids 并入 L |
| 改挂线 `reattach` | 把某事件从一条线移到另一条，或增/删它的挂线 | 线留新版本 |
| 关线 `closeLine` | `active → closed`（核心活动已结束） | 留痕 |
| 重开线 `reopenLine` | `closed → active`（她要把新活动接回旧线，§5.5.3） | 线留新版本 |

线的版本淘汰规则与事件一致（§14 D4）：她的修正不淘汰。

## 8. 指针链：纯链式（v0.1 的"捷径"已移除）

```
记忆本条目 ──→ 事件块 ──→ 记录本条目 ──→ 资产（字节）
```

### 8.1 为什么去掉捷径（用户 2026-11-09 的关切是对的）

用户指出：如果文件被删，扁平结构会有**三处**悬空（记忆、事件、记录各存一份状态），链式只有**一处**（记录本的 MediaRef）。

这个直觉成立，且比"跳层成本"更要紧：

| | 扁平（各层存状态） | 纯链式 |
|---|---|---|
| 文件被删 | 3 处标 lost，可能出现"记忆说已保存、记录说已丢失"的矛盾 | 1 处标 lost，唯一权威 |
| 状态不一致风险 | 有（要同步 3 份） | 无（只有 1 份） |
| 取证路径 | 1 跳 | 2–3 跳，但都是本地索引查询（毫秒级，非网络往返） |

**结论：存储链式、读取扁平。** 写入时只存"指向上一层"，不存冗余状态；读取时（复盘、注入、做梦）把链一次性解析、在内存里组装成扁平视图给对方用，**但不写回存储**。

### 8.2 链式必须配的三条纪律

1. **下层被删不得静默**：删除必须留下悬空状态（如 `原件已不可读`），上层条目保留，不连带删；
2. **上层指针不自动改写**：见 §7.3；
3. **逐级可校验**：任一层可独立回答"我指向的东西现在还在不在"，且答案是唯一真相（不缓存结论）。

## 9. 媒体与资产（沿用 A 块定案稿 §6，用户 2026-11-09 确认按原定）

### 9.1 已有设计（不是本稿新增）

- 真源只存 `MediaRef`（`ref_id / kind / mime / bytes / sha256 / origin`），字节进资产层；
- 摄入时字节拷入 **staging**；**只有她**能调 `preserveMedia` 把 staging → `assets`（长期保存），系统**永不自动长期保存**；
- 未采纳的 staging 到期清除（30 天），台账留痕；
- 状态是折叠不是字段：`origin-only / staged / preserved / decayed / lost`；
- 诚实边界：注入时如实说"照片（本地已保存）/（原始已不可考，未保存副本）/（链接，未取回内容）"，**不假装还看得见**。

### 9.2 "存本地带上限"的落法（D1 已定：甲方案）

用户表述"确认存本地带上限"与定案稿"系统永不自动长期保存"的张力，按**甲方案**收口：

- **上限只作用于 staging**：暂存区有配额，超限淘汰**最久未被采纳**的，淘汰记台账；
- **长期区（assets）不受系统配额**：只由她保存、只由她删除；
- 效果：磁盘可控，而"留什么"仍归她决定。

### 9.3 媒体挂在记录本，不挂在事件块

- 记录本那条记 `MediaRef[]`（3 张图 = 3 条引用；语音/视频/文件同理，`kind` 是开放枚举）；
- 事件块只记指向记录本的指针，**不重复抄媒体信息**；
- 字节按内容哈希命名，同一文件重复收到不存两份；
- 外部原件失效 → `lost`，如实标注，不伪造。

## 10. 标签中性化（用户 2026-11-09 提出，三条硬规则）

1. **只描述可观察属性，不描述价值**。禁止：`重要` / `高价值` / `值得记`。
2. **标签只作检索维度，不作排序维度**。复盘是她读事件，不是系统按标签取 top N。
3. **标签不进注入**。不能因为贴了标签就在对话里优先呈现。

补充：标签没有分数、没有权重、没有先后。多标签各自独立（用户已确认）。

**执行时机（v0.5 明确，P3-11）**：

| 标签 | 性质 | 谁打、何时打 |
|---|---|---|
| `带附件` / `跨通道` | 纯机械，可观察 | 事件闭合时由规则**零成本**打，纳入本稿 |
| `话题跳转` | **打点是机械的（记录话题边界位置），信号本身是语义的**——它是 B 类语义候选的触发记录，不据此自动切分 | 闭合时机械打点，是否成边界归她 |
| `与前事矛盾` | 语义判断（要理解上下文才能判） | **移出本稿，归复盘那稿**——规则层做不了，留在本稿会破坏"实时零 LLM" |

## 11. 失败与兜底

| 失败 | 后果 | 兜底 |
|---|---|---|
| 切太碎 | 复盘碎，但不错 | 可合并；"低置信不切"能防 |
| 切太大 | 复盘粗 | 可拆分 |
| 实时没切（进程没起来） | 记录本仍完整 | 下次启动补切（§7.4） |
| 用户离开后无下一条记录 | 旧实现下静默不求值、事件延迟到次日 | **时钟 worker 按 `now - 末条记录 ≥30min` 补闭合**（§5.2）；worker 挂了重启后由 §7.4 补切 |
| 事件 raw 超模型上下文 | 摘要调用超长/失败 | 硬保险丝 50k tokens 先闭合（§5.2），不靠摘要分层 |
| 后台 LLM 慢/挂 | 事件已闭合但暂没摘要 | 不阻塞对话；`pending` 退避重试，事后补齐，不伪造 |
| 切错且很久后才发现 | 事件里混了别的 | 改边界 + 重跑派生字段 + 留版本；不做静默重算 |
| 事件层损坏 | 二级真源丢失 | 靠备份；投影/索引可重建，事件不可重建 |
| 孤立记录无法归并 | 一直挂着 | 保持孤立、复盘可见、她手动归并，不自动并入 |

## 13. 明确不做

- 不做"事件质量分"或"事件重要性排序"；
- 不在摄入热路径调 LLM（机械信号即时闭合，LLM 只在后台异步队列）；
- 不让算法覆盖已有事件；
- 不在事件块里存媒体字节；
- 不在事件块里写她的感受（那是复盘产物）；
- 不把跨时段的两段合成一个事件（时间范围只装真实交互的那一段，中间空档不算进任何事件）；
- 不用纯规则或 embedding 直接决定话题线归属（embedding 只产候选，最终由 LLM 判定、她在复盘时可改）；
- 不写"三要素规则检查器"或字数硬下限（规则判语义就是定式；LLM 自检 + 她复核）；
- 不自动把孤立记录并入内容无关的事件；
- 不自动改写她的上层指针、不自动重连挂线（修正只由她发起）；
- 不做 2 小时时间轴看门狗（v1.3 否决理由修正：静默管相邻记录间隔、存活看门狗管事件跨度，二者逻辑不冗余；但 2h 看门狗的有效覆盖全落在**无害的低速稀疏长聊**——每 20 分钟一条、持续 8 小时的事件本就低密度、摘要无压力；而有害的高速深聊由 7000 字上限抢先覆盖。它要防的场景不需要它，需要它的场景又防不住）；
- 不做事件内"摘要分层"（v1.3 否决：在有效对话 ≤7000 字且 raw <50k tokens 的边界内 600 字摘要够用；超 raw 由硬保险丝先切，不靠分层落盘）；
- 不做独立的 LLM 细分阶段（v1.3 否决：慢路径改 pointers 违反 §6.1.1；细分能力并入摘要调用的非权威候选，且少一次调用、不要求序号精确写入）；
- 不在本稿范围内做复盘三层、做梦、倾向强度、污染防护。

## 16. 实现分期与质量回路（落地建议）

### 16.1 分两期实现，schema 一次到位

话题线是**附加元数据**——挂线不改事件内容、字段可空、可事后回填，所以：

| 阶段 | 范围 | 目的 |
|---|---|---|
| **第一期（已交付，commit ba33c30）** | 切分（机械闭合 + 语义候选标记）+ 闭合异步摘要 + 五种事件修正 | 让复盘先有合格的事件输入，端到端跑通 |
| **下一期（v1.3 范围）** | **阶段 0 工具轮类型化（§5.0）+ 切分量纲改有效对话 7000 字 + 静默时钟化 + 硬保险丝 + 摘要调用输出非权威话题候选（同版本写回）+ 任务闭环作用域判据（验证后激活）** | 纠正工具轮错标、把压缩比钉在 ≤11.7:1、消除记忆延迟、唤醒休眠信号 |
| **第二期** | 话题线（原始记录 embedding 投票 + LLM 判定 + 线的修正）、D11 embedding 互信息突变 | 补跨时段/跨通道的连续性，接回被拆分的片段 |

**v1.3 对"schema 一次到位"的精确口径（审计修正）：** v1.3 不是零 schema 变更，而是**一次 schema 窗口内的加法**——只加可空字段与枚举值，**不升 `schema_version`**（写点全在本仓、无第三方写者；反向条件：新增非空字段或第三方写 events/ 时才升版）。具体条目：

- 契约枚举：`closed_reason` 加 `max-dialogue-chars` / `max-chars`，`max-records` 保留为兼容值不再产生；
- 契约字段：Experience 加 `char_count`（number，工具轮 0），Event 加 `effective_chars`（可空）；
- 摘要契约：`LLMSummarizeResponse` 加候选字段、`SUMMARY_PROMPT_VERSION` bump v2；
- 投影：SQLite 事件表新增对应列（既有纯加法 `addMissingEventColumns` 路径），编码往返与旧行兼容——旧行两字段为 `null`，读取按"未统计"处理，不强制回填。

**v1.1 追加**：`summary_prompt_version` / `summary_model` 两个**可空溯源字段**同样在第一期就建成写入（它们不是"留空"字段——后台每写一条摘要就填一次；她手写摘要时为 `null`）。

### 16.2 历史回填的预期：初始会很碎，属正常

现有 247 条里不同来源的相邻记录可能相隔数天，按"静默 ≥30 分钟即闭合"回填，会产出**大量单条事件和孤立记录**，之后再靠话题线和她的手动合并逐步收拢。这是设计使然，**不是 bug**——比起一开始就硬凑出错误的大事件，先忠实切分、再逐步归并更符合"诚实优先、宁缺勿凑"。

### 16.3 零分数的质量回路（不加分、不自动调）

不做任何事件评分或加权，但把**她的修正率**作为离线观测指标：

- 合并频发 → 说明切得太碎（30 分钟静默/7000 有效字偏紧）；
- 拆分频发 → 说明切得太粗（或摘要候选提示的转折位置未被采纳）；
- 据此由**人工**调整阈值，**不做自动调参**——保持"算法不重写事件"的纪律，参数调整只影响以后新切的事件。
