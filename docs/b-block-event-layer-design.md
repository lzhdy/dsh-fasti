## 0. 一句话总览

**记录本存流水（一条一条，带时间点），切分员用零成本信号把流水聚成事件（一件一件，带时间范围），事件一闭合就由 LLM 生成一次客观摘要、提取事件锚点，并判定它挂到哪条网状话题线上；记事本存事件，筛选员只贴中性标签；复盘时她消化并写进记忆本。事件是二级真源——写进去就不许算法重算，只许她修正。**

## 1. 三层命名与职责（必须先定，否则实现方必乱）

| 层 | 用户说法 | 里面是什么 | 粒度 | 时间形态 | 现状 |
|---|---|---|---|---|---|
| 第一层 | **记录本** | 一条一条的流水：谁 几点 在哪 说了什么 / 做了什么 / 用了什么工具 / 上了哪个网页 / 看了什么 | 一条消息、一次动作 | 单点时刻 | **已有**，即代码里的 `experiences`（247 条），需补类型 |
| 第二层 | **记事本** | 一件一件的事：一段对话、一次浏览、一次一起做的事 | 一个事件 | 时间范围 `[start, end]` | **新建** |
| 第三层 | **记忆本** | 她真正记住的：事实、对关系的理解、自我认知、三观、倾向 | 一条记忆 / 一条人格主条目 | 无固定形态 | 旧系统有，B 块接新地基 |

**两个加工角色**：事件切分员（流水 → 事件）、筛选员（事件 → 中性标签）。**一次消化**：复盘。

### 1.1 命名冲突的处置（重要）

旧骨架里"记事本升级成 MP4（存指针不存像素）"指的是**记忆单元**。按新流程，媒体能力应挂在**记录本**——因为只有原始记录才承载字节引用，事件块只存指向记录本的指针。

**处置**：`记事本` = 事件层（本稿）；`记忆本` = 沉淀层；媒体引用能力绑在 `记录本`，向上逐层只透传指针。

## 2. 为什么必须切事件（问题陈述）

现在 247 条记录 = 247 条消息，一条 user 一条 assistant 各算一块。按这个粒度复盘，会出三个问题：

1. **碎**：一次 20 句的对话被切成 20 个"经历"，复盘要自己在脑子里拼上下文；
2. **错位**：user 那条和 assistant 那条被当成两件事，而它们本来是同一件事的两半；
3. **无法回答"发生了什么"**：记录本能回答"第 42 条说了什么"，回答不了"那天我们聊了什么"。

事件层就是为了把"流水"熬成"事"。用户 2026-11-09 明确：**"整个程序都是在一段一段经历上进行的"**——事件是复盘、筛选、做梦、回忆的公共输入单位。

## 3. 事件是什么

### 3.1 定义

一个事件 = 记录本里**连续的一段**，满足：它讲的是同一件可命名的事。

### 3.2 事件字段（对应 27 条第 14 条）

| 字段 | 含义 | 何时产生 |
|---|---|---|
| `summary` | 一句话摘要，**客观语气、第三人称、不带评价** | **事件闭合时一次生成**（§6.2） |
| `key_points` | 关键点 / 关键数据（数组，可空） | 同上 |
| `pointers` | 原文指针组：指向记录本的具体条目 | 边界确定时（必需） |
| `status` | 状态机（§3.4） | 维护 |
| `time_range` | `[started_at, ended_at]`，允许为零长度 | 边界确定时 |
| `assembled_at` | 被切成事件的时刻（与 `time_range` 是两条轴） | 边界确定时 |
| `anchors` | 事件锚点：具体动作 / 事实进展 / 计划（数组），用于话题线判定（§5.5） | 事件闭合时，与摘要同一次调用 |
| `topic_lines` | 所属话题线 id 列表（**网状，可多条**），见 §3.5 | 事件闭合时 LLM 判定 |

> 骨架原写"重要性"为六要素之一。**本稿确认删掉**：真源层一旦带"重要性"就等于预设了什么重要（撞红线②）。她的判断落在复盘产物里，不落事件块字段。

### 3.3 时间形态（用户 2026-11-09 确认 + 三点补充）

- 记录本：一条一个**单点时刻**（已有 `occurred_at`）；
- 事件块：一个**时间范围**，允许 `start == end`（瞬时事件，如"她打开了一个网页"）；
- **双轴不混**：`time_range` 是"事何时发生"；`assembled_at` 是"何时被切成事件"；
- **不按日历切，按静默切**：聊到凌晨跨零点不因日期变化切成两个事件；但中间静默 ≥30 分钟就闭合。日历不是判据，静默才是（§5.5）。

### 3.4 状态机

```
open ──(静默/闭环)──→ closed ──(做梦/淘汰)──→ archived
  │                    │
  └──(她重开)───────────┘
                       └──(合并)──→ merged（带指向新事件的指针）
                       └──(拆分)──→ split（带指向子事件的指针）
```

- `open`：可能还有后续，回补原文时应并入；
- `closed`：已判定结束，正常复盘对象；
- `merged / split`：**被修正后的退役态**，自身不删，保留指向新事件的指针，供上层接力。

### 3.5 话题线（横向，网状）

事件块除了纵向的指针，还有一个**横向**归属：`topic_lines`。它把"同一件事在不同时间、不同通道里的多个片段"归到同一条线上。

**它是网状，不是单链**：一个事件可以同时属于多条话题线（比如"装修"和"和她的关系"两条线在同一件事上交汇）。

话题线是独立对象，最小结构：

```
TopicLine {
  id
  core_activity     核心活动是什么（一句话，由 LLM 写，随新事件可更新）
  event_ids[]       线上的事件，按时间排列
  status            active / closed
}
```

它与 §8 的"指针链"是**两回事**，务必分开命名，否则实现方必混：

| | 方向 | 连接什么 | 用途 |
|---|---|---|---|
| **指针链**（§8） | 纵向 | 记忆 → 事件 → 记录 → 资产 | 定位、取证、状态唯一真相 |
| **话题线**（本节） | 横向 | 事件 ↔ 事件（围绕同一核心活动） | 复盘/检索时把一件事的多个片段一起理解 |

话题线只在**横向**上成立：它不影响纵向的定位与状态，删掉话题线最多让复盘少一条线索，不会让取证失败。

**与旧 v0.3"接续指针"的差别**：旧设计是事件两两互指（previous/next），只能连成单链；新设计是事件挂到独立的话题线对象上，天然支持多线、分支与交叉，且 `core_activity` 让"这条线到底在讲什么"有明确答案。

## 4. 存储定位：二级真源（本稿最核心的一条）

| 候选 | 若按此做会怎样 | 结论 |
|---|---|---|
| 当投影 | 切分算法一升级就全量重算，**她改过的边界被抹掉** | 否 |
| 当一级真源 | 无意义——事件本身就是从流水派生的 | 否 |
| **当二级真源** | 派生自记录本，但**一旦写入即固化**；只允许她的修正与版本推进 | **采用** |

推论（写进实现纪律）：

1. 事件**不可由算法批量重建**；重建只允许"补齐缺失事件"（§7.3），不允许覆盖已有事件。
2. 事件必须**版本化**：每次边界修正留新版本，默认保留 10 版（沿用做梦的回滚深度）。
3. 事件层备份的重要性 = 真源级，不是索引级。

## 5. 切分判据

### 5.1 主判据（她做语义判断，但不是每轮都判）

从一个具体事件转到另一个；或前一件事已闭环（问题解决、话题收尾、约定达成后执行完）。

### 5.2 辅判据（零成本信号，只产生候选边界，不产生切分结果）

| 信号 | 阈值/用法 | 依据 |
|---|---|---|
| **时间间隔** | ≥ **30 分钟**，闭合当前事件 | memv 默认 `time_gap_minutes=30`；gleanr 默认 `max_time_gap_seconds=1800` —— 两家独立实现同值 |
| **条数上限** | 单事件 ≤ **20 条记录**（约 10 轮对话），超限强制闭合 | gleanr `max_turns=6`（决策跟踪场景）、memv `segmentation_threshold=20`；取 20 更贴合日常闲聊密度 |
| **任务闭环** | 工具调用/一次任务完成即闭合 | gleanr `close_on_tool_result=True` —— "事办完了"是最自然的边界 |
| **场景切换** | 会话切换、通道切换（dsh → browser → camera） | 旧稿 §5.1；ES-Mem 的 `TOPIC_SHIFT` 标签 |
| **话题/意图突变** | 只标记"可能边界"，不硬切 | ES-Mem 用互信息突变取候选 + LLM 复核；我们只取候选 |

**关键纪律**：辅判据**只产生候选边界**，不产生切分结果。宁可不切（事件偏大），不可乱切。

### 5.3 防误切（已核对五家做法）

1. 问候、客套、寒暄**不单独成事件**（并入相邻事件）；
2. **单条不孤立**：一条记录若前后都没有可并的，先挂"待归并"，不进记事本（gleanr 的 `min_episode_turns` + carry-forward 同思路）；
3. 低置信**不切**；
4. 边界候选必须能被她的修正覆盖。

### 5.4 一次对话的默认形态（示例，供评审）

```
记录本：
  t1 user "帮我看下这个配置"
  t2 her  "这里少了个括号"
  t3 user "改好了，谢谢"
  t4 her  "不客气"
事件块（一个）：
  summary   "用户请她检查配置，她指出缺少括号，用户自行改好后致谢"
  time      t1 ~ t4（约 3 分钟）
  pointers  [t1,t2,t3,t4]
```

### 5.5 跨时间段：切开，再用话题线接上

旧稿 §5.3 提过"跨会话同一件事接续"，v0.4 按 Membox（§15）的两段式机制重写。

#### 5.5.1 三种会遇到的形态

| 形态 | 例子 | 错误做法 | 本稿做法 |
|---|---|---|---|
| **跨天 / 长静默** | 昨晚聊装修聊到一半，今早接着说 | 合成一个事件，`time_range` 跨 12 小时、中间全空 | 两个独立事件，挂到同一条话题线 |
| **跨通道** | 在 dsh 里他说"我查一下"，然后她真的开了浏览器查，回来接着说结果 | 切成三个互不相关的事件，复盘时看不出是一件事 | 三个事件 + 同一条话题线，复盘时按线一起读 |
| **历史数据不连续** | 迁来的 247 条里，不同来源的相邻两条可能相隔几天 | 按"相邻就并入"硬凑 | 静默 ≥30 分钟即闭合，不因来源特殊 |

#### 5.5.2 为什么必须切开而不是合并

合并时间范围会带来三个失真：

1. **统计失真**：一个事件说"持续 12 小时"，实际只有前后各 10 分钟在人；
2. **检索失真**：按时间范围查"那天下午在干什么"，会捞出一个跨了两天的巨型事件；
3. **摘要失真**：600 字上限装不下两天的内容，必然写空话。

所以：**时间范围只装真实发生过交互的那一段；中间的空档不算进任何事件。**

#### 5.5.3 话题线怎么判定：embedding 候选 + LLM 判定（不写规则）

v0.3 曾用"四条硬信号纯规则"，问题是规则只能抓表面信号、抓不到"语义同一件事但表面不相似"，而且规则本身就是定式。v0.4 改为两段式：

**第一步 · 事件闭合时提取锚点**（与摘要同一次 LLM 调用）：

```
anchors = 具体动作 / 事实进展 / 计划
例：{动作: "她查了北欧风案例", 进展: "用户准备下周定装修方案", 待办: "约工长"}
```

**第二步 · embedding 投票，只产生候选**：

- 每个新锚点用 embedding 余弦相似度，找最相似的已有话题线；
- 一个锚点投一票，取并集得到候选话题线集（**embedding 不做最终决定**）。

**第三步 · LLM 批量判定**：

- 把候选话题线的完整事件 + 新事件全部锚点给 LLM；
- LLM 判断新事件该挂到哪条线（或开新线），**一个事件可挂多条线**。

**LLM 的判据（核心：区分"话题相似"和"核心活动延续"）**：

| 挂线（任一成立） | 不挂线（任一成立） |
|---|---|
| 延续**同一核心活动**（不是相似话题） | 发起新的独立活动，即使话题相似 |
| 提供进展 / 结果 / 解决方案 / 直接后果 | 平行但独立的事件 |
| 逻辑或时间上的自然后继 | 没有具体进展的通用回应（"好的""嗯"） |
| 属于同一待办的下一步 | 只在表面词汇上相似 |

未被任何线接受的事件 → LLM 开新话题线。

#### 5.5.4 话题线的四条纪律

1. **不改写**：话题线归属一旦写入，后续事件合并/拆分时**不自动重连**，解析时顺线走（同 §7.2）；
2. **不闭环**：事件 → 话题线的归属必须是有向无环，发现成环即视为数据损坏，标记待她修；
3. **悬空留痕**：线上某个事件被删 → 标注"该事件已不可读"，话题线与其他事件保留，不连带删（同 §8.2）；
4. **核心活动可更新但留版本**：新事件让 `core_activity` 含义变化时，更新描述并留旧版，不静默覆盖。

#### 5.5.5 示例

```
话题线 L7  core_activity = "装修：从看风格到定方案"
  事件 E1  10-08 21:40 ~ 22:20  "聊装修风格，用户想先看北欧风案例"
  事件 E2  10-09 09:10 ~ 09:35  "她查了北欧风案例发给用户"
  事件 E3  10-09 20:05 ~ 20:40  "用户选定风格，决定下周约工长"
  L7.event_ids = [E1, E2, E3]

复盘读到 E1 时，话题线告诉它"这件事有后续 E2、E3"，三段一起理解，
但每个事件的 time_range 各自只装真实交互的那段。
```

## 6. 切分与摘要的执行路径（v0.2 的关键修正）

### 6.1 三段时间线

| 时机 | 做什么 | 调 LLM？ | 成本 |
|---|---|---|---|
| **摄入时（实时）** | 记录本追加一条 → 并入当前 `open` 事件 → 命中辅判据则闭合／开新事件 | **否** | 零 |
| **事件闭合时** | 一次 LLM 调用完成：生成 `summary` + `key_points` + `anchors`，并做话题线判定（embedding 投票 + LLM 判定） | **是，一次** | 每事件一次 |
| **复盘时** | 她合并/拆分/改边界/重写摘要 | 是（复盘本身） | 批次 |

### 6.2 为什么摘要不在实时生成（v0.1 的错误，已修正）

v0.1 曾写"实时模板拼接摘要"。**这条被否定**，理由：

1. 模板拼接就是定式判断——把"谁说了什么"机械套进句式，遇多轮交错、多话题、附件、工具调用就必然失真；
2. 业界的摘要**全部由 LLM 生成**，且**都在事件闭合后做**，没有在每条消息进来时生成的：
   - **Nemori**：episode 关闭时由 `Episode Generator` 生成"标题 + 第三人称叙事"；
   - **memv**：`EpisodeGenerator` 在 episode 形成时生成 Title + third-person narrative；
   - **gleanr**：episode 关闭触发 reflection，`background=True` 异步提取，不阻塞对话；
   - **ES-Mem**：Level-2 `Event Summaries` 由模型生成，且实测去掉摘要后单跳任务显著下降。
3. "闭合时一次"同时满足两件事：**质量**（LLM 写客观摘要）、**成本**（不是每轮，是每事件一次）。

### 6.3 降级

若闭合时没有可用模型（未配置 / 调用失败）：写入 `summary: null` + `summary_quality: "pending"`，事件照样可用（靠指针回原文）。**事后补齐**一次，不阻塞、不伪造占位文案。

### 6.4 摘要的写法约束与字数

**先定原则：字数只做纯技术兜底，不做语义判定；写多长由 LLM 按实际信息量决定。**

v0.3 曾按"记录条数"分档，问题是**条数不等于信息量**——20 条记录可能全是语气词、表情、无意义寒暄，按条数定字数必然注水。v0.4 取消分档：

**两条技术线（只防空、防转录，不评价内容）**：

- **硬上限 600 字**：超过就是转录，不是摘要，拒绝；
- **硬下限 15 字**：低于 15 字说明没抓住事，重生成。

**写多长，交给生成摘要的 LLM**，prompt 里写清：

1. 语气词、表情、无意义寒暄（"嗯""哈哈""好的"）不进摘要；
2. 按实际信息量自然写，**能短则短**；
3. 必须覆盖三要素：**谁 / 做了什么 / 结果如何**。

**三要素齐不齐，不写规则检查器**——规则判语义就是定式。两个出口：

1. 摘要本来就是 LLM 写的，让它在**同一次调用里输出前自检**，不另造检查器；
2. **她在复盘时是最终裁判**，觉得没抓住事就重写。

对照示例（同一个晚餐事件）：

```
✓ 合格（32 字）：用户问晚餐吃什么，她列了三个选项，用户说再想想。
✗ 注水（85 字）：用户在这个晚上提出了关于晚餐饮食选择方面的问题，
  希望得到一些有建设性的意见。针对这个问题，她进行了认真的思考……
✗ 残缺（12 字）：聊了晚餐。
```

写法要求（三条）：

1. 第三人称、客观、只写发生了什么与关键数据；
2. **不写评价、不写她的感受、不写"重要"**（感受是复盘的事，见 27 条第 23 条）；
3. 单一事件内若有多个话题转折，按"先做什么、后做什么"顺叙，不展开对话细节。

## 7. 修正链路（一等能力，不是补丁）

### 7.1 四种修正

| 操作 | 语义 | 留痕 |
|---|---|---|
| 合并 | A + B → 新事件 C；A、B 置 `merged`，带 `merged_into: C` | 旧事件不删 |
| 拆分 | A → B1 + B2；A 置 `split`，带 `split_into: [B1,B2]` | 旧事件不删 |
| 改边界 | 把首/末 N 条记录挪出或挪入 | 新版本 |
| 重开 | `closed → open` | 新版本 |

### 7.2 上层指针的接力规则

记忆本里的记忆指向事件 A，A 后来被合并成 C：

- **不自动改写记忆的指针**（那是她的东西，不能替她改）；
- 记忆 → A 的指针解析时，顺着 `merged_into` 追到 C，**只读不写**；
- 注入时如实呈现："这条记忆来自一件后来被合并的事"。

### 7.3 允许"补齐"，不允许"重建"

- 允许：发现某段时间的记录没有任何事件覆盖 → 补切一段（幂等，按记录 id 去重）；
- 禁止：拿全量记录重跑切分算法去覆盖已有事件。

## 8. 指针链：纯链式（v0.1 的"捷径"已移除）

```
记忆本条目 ──→ 事件块 ──→ 记录本条目 ──→ 资产（字节）
```

### 8.1 为什么去掉捷径（用户 2026-11-09 的关切是对的）

用户指出：如果文件被删，扁平结构会有**三处**悬空（记忆、事件、记录各存一份状态），链式只有**一处**（记录本的 MediaRef）。

这个直觉成立，且比"跳层成本"更要紧：

| | 扁平（各层存状态） | 纯链式 |
|---|---|---|
| 文件被删 | 3 处标 lost，可能出现"记忆说已保存、记录说已丢失"的矛盾 | 1 处标 lost，唯一权威 |
| 状态不一致风险 | 有（要同步 3 份） | 无（只有 1 份） |
| 取证路径 | 1 跳 | 2–3 跳，但都是本地索引查询（毫秒级，非网络往返） |

**结论：存储链式、读取扁平。** 写入时只存"指向上一层"，不存冗余状态；读取时（复盘、注入、做梦）把链一次性解析、在内存里组装成扁平视图给对方用，**但不写回存储**。

### 8.2 链式必须配的三条纪律

1. **下层被删不得静默**：删除必须留下悬空状态（如 `原件已不可读`），上层条目保留，不连带删；
2. **上层指针不自动改写**：见 §7.2；
3. **逐级可校验**：任一层可独立回答"我指向的东西现在还在不在"，且答案是唯一真相（不缓存结论）。

## 9. 媒体与资产（沿用 A 块定案稿 §6，用户 2026-11-09 确认按原定）

### 9.1 已有设计（不是本稿新增）

- 真源只存 `MediaRef`（`ref_id / kind / mime / bytes / sha256 / origin`），字节进资产层；
- 摄入时字节拷入 **staging**；**只有她**能调 `preserveMedia` 把 staging → `assets`（长期保存），系统**永不自动长期保存**；
- 未采纳的 staging 到期清除（30 天），台账留痕；
- 状态是折叠不是字段：`origin-only / staged / preserved / decayed / lost`；
- 诚实边界：注入时如实说"照片（本地已保存）/（原始已不可考，未保存副本）/（链接，未取回内容）"，**不假装还看得见**。

### 9.2 "存本地带上限"的落法（D1 已定：甲方案）

用户表述"确认存本地带上限"与定案稿"系统永不自动长期保存"的张力，按**甲方案**收口：

- **上限只作用于 staging**：暂存区有配额，超限淘汰**最久未被采纳**的，淘汰记台账；
- **长期区（assets）不受系统配额**：只由她保存、只由她删除；
- 效果：磁盘可控，而"留什么"仍归她决定。

### 9.3 媒体挂在记录本，不挂在事件块

- 记录本那条记 `MediaRef[]`（3 张图 = 3 条引用；语音/视频/文件同理，`kind` 是开放枚举）；
- 事件块只记指向记录本的指针，**不重复抄媒体信息**；
- 字节按内容哈希命名，同一文件重复收到不存两份；
- 外部原件失效 → `lost`，如实标注，不伪造。

## 10. 标签中性化（用户 2026-11-09 提出，三条硬规则）

1. **只描述可观察属性，不描述价值**。允许：`带附件` / `话题跳转` / `跨通道` / `与前事矛盾`。禁止：`重要` / `高价值` / `值得记`。
2. **标签只作检索维度，不作排序维度**。复盘是她读事件，不是系统按标签取 top N。
3. **标签不进注入**。不能因为贴了"可能重要"就在对话里优先呈现。

补充：标签没有分数、没有权重、没有先后。多标签各自独立（用户已确认）。

## 11. 失败与兜底

| 失败 | 后果 | 兜底 |
|---|---|---|
| 切太碎 | 复盘碎，但不错 | 可合并；"低置信不切"能防 |
| 切太大 | 复盘粗 | 可拆分 |
| 实时没切（进程没起来） | 记录本仍完整 | 下次启动补切（§7.3） |
| 闭合时模型不可用 | 没摘要 | `summary_quality: pending`，事后补齐，不伪造 |
| 切错且很久后才发现 | 事件里混了别的 | 改边界 + 留版本；不做静默重算 |
| 事件层损坏 | 二级真源丢失 | 靠备份；投影/索引可重建，事件不可重建 |

## 13. 明确不做

- 不做"事件质量分"或"事件重要性排序"；
- 不在实时阶段调 LLM（边界候选化只用零成本信号）；
- 不让算法覆盖已有事件；
- 不在事件块里存媒体字节；
- 不在事件块里写她的感受（那是复盘产物）；
- 不把跨时段的两段合成一个事件（时间范围只装真实交互的那一段，中间空档不算进任何事件）；
- 不用纯规则或 embedding 直接决定话题线归属（embedding 只产生候选，最终由 LLM 判定、她在复盘时可改）；
- 不写"三要素规则检查器"（规则判语义就是定式；LLM 自检 + 她复核）；
- 不对一句话的短事件强制注水到最低字数；
- 不在本稿范围内做复盘三层、做梦、倾向强度、污染防护。
