## 2. 逐条复核

### Q1 升版口径

- **洞 1.1（成立，建议升为阻塞内附带条款）**：charter §3 步 5 只写「由离线重建 CLI 从真源重建 FTS（抄本可弃，4.4）」，§3 步 3 只改 `schema.ts` 定义，确未写 DROP+CREATE。SQLite FTS5 `tokenize=` 建表后不可变、`CREATE TABLE IF NOT EXISTS` 对已存在 trigram 表空操作——诊断正确。**补充 S1**：DROP+CREATE+重灌+校验须在**同一 SQLite 事务**内完成，提交前跑一次 MATCH 抽样；否则中途失败会留下「表在、内容空」的 v3 库，正好落进洞 1.2 的静默空结果场景，而窗口态防护此时救不了（表已存在且看起来是 v3）。
- **洞 1.2（成立但需修正表述）**：外审稿说 charter「没定义未重建窗口怎么办」——**部分不确**：§5 红测 6 明确「v2 库在 v3 代码下被识别为需重建、不得静默查询」，已有约束。真正缺的是：(a) 拒绝的**显式语义**（必须是「需离线重建」错误，不是通用异常或空结果）；(b) **读路径规范**（取卡、原文复核可继续服务）；(c) 与「宁空勿错」的区分措辞。建议按修订清单的增补文本写死，但严重度理由改为「约束存在但语义不精确」，避免主控以「红测 6 已覆盖」驳回而冲淡真正问题。
- **洞 1.3（成立）**：读实时 `tokenize=` 比对版本戳，成本极低，与洞 1.2 共用同一拒绝通道即可。建议把它并入洞 1.1 的验收断言（同一处读 `sqlite_master`），不要散成两个独立条款。
- **Q1 处置复核**：「卡行不跟」采纳；「库版本即迁移充分信号」不采纳——维持。

### Q2 宽窄边界

- **洞 2.1（成立，且必须进阻塞清单）**：2 字 CJK 词 bigram 化后仅一个单元，phrase 对单单元无义，原文复核是唯一精度护栏——技术判断正确。但 charter §5 红测 4 已有「投毒样本必须被复核拒收」，所以这是**红测 4 的显式扩充**（补「单 bigram 命中含该字但非该词的异卡」正反例）＋§7 加注，不是新建机制，工作量很小。**外审稿处置建议的阻塞清单漏列此项**（只列了 1.1/1.2/2.2/R1/R2），而其正文标「高」、Q2 处置称「本卡自身必须闭合」、修订清单也标 🔴——三处自相矛盾，回收前必须统一为六项。
- **洞 2.2（成立，但指标口径未定义到位）**：「2 字查询首次进 FTS、bigram 最低 IDF、把空结果换成可能错结果」判断正确。但修订清单建议「N 取现 trigram 基线，不得高于此」存在陷阱：trigram 下 2 字查询**本就 0 结果**，若「误召」按 FTS 原始命中定义，基线为 0，任何非空错误命中都失败，与召回目标直接冲突；若按门后错卡定义，则可行。**补充 S2**：验收口径须明确区分「门后错卡率」（验收量，可设上界）与「FTS 候选膨胀率」（观测量，只记录），并写明题库与 N 的取值方法。**补充 S3**：charter §3 步 1「ASCII/数字整词保留」＋阈值 2，使 2 字母 ASCII 功能词（to/of/in/is）同样首次进入 FTS，与 2 字 CJK 同属低 IDF 族——误召口径与红测须一并覆盖，外审稿只写了 CJK。
- **洞 2.3（成立，建议级）**：「孤立单字段」与「长段内逐字补底」未区分属实。补充：§5 红测 1 的「单字」用例必须同步限定为孤立单字段，否则红测与实现口径打架。
- **Q2 处置复核**：「2.1/2.2 不能留给拆句工」成立；「宽窄切分采纳」成立。

### Q3 时序

- **Q3a 先于 P6（采纳）**：无异议。
- **洞 3.1（部分成立，诊断需改）**：charter §4 明确「本卡不把 P6 当验收前置」，依赖方向是**本卡 → P6 → 拆句工**的单向链，不是环。外审稿「时序图是环不是链」的论断不成立。**实质风险仍成立**：P6 在本卡合并后的几何上出题，若本卡误召偏差（洞 2.2）未被度量，会被固化进金标阈值。处置应采用外审稿自己给的轻量方案 B——把「P6 出题发现几何偏差则回退本卡修正、P6 暂不出题」写进 §4 与 §7 挂账③；「小型 holdout 精度门」不另立，作为洞 2.2 精确率口径的副产品即可。严重度维持 🟡 建议，**不列阻塞**。
- **洞 3.2（成立，建议级）**：§5 红测 3/4 对 cue 文本形态敏感，而红测语料来源未明（E-8 为同一批真模型 cue）；§6 又要求「离线复跑探针 oracle ≥23/25」，本身绑定现有 cue 集。二选一须写死；考虑到探针验收的绑定关系，倾向「锁定合成 cue 集并保留探针为独立回归」或明确承诺 #123 解冻后复跑。此项与上一轮双路线评审 Q9「A 生效后基线污染」同源，建议主控一并登记。

### 反对意见与签认栏

- **R1（成立，阻塞）**：§8 三问 vs §9 五问属实。补：外审稿已用「红线红绿灯」「最坏回滚」两节实质补齐其中两问，「实测数据」一问仍只有 R3（建议级）——因此 **R1 的闭合条件是洞 2.2 先产出精确率数字**，二者绑定，不能先签 R1 再等 R3。
- **R2（成立，阻塞）**：补：静态扫描（gate.ts/rules 不引用 `MIN_FTS_CODEPOINTS`/几何常量）与行为红测（同 cue 集门裁决逐条相等）**两条都要**，单做其一不足以证明「间接未破坏」。
- **R3（成立，但处置错误）**：外审稿处置建议把 R3 列为「延后/降为建议」，与其自身 R1「实测栏填不出精确」的分析、以及修订清单「R3 并入洞 2.2 执行」的处理冲突。复核裁定：**R3 不延后，随洞 2.2 在阻塞项内闭合**；请主控以修订清单而非外审稿处置建议为准。
- **R4（成立，备注级）**：补：把「不引入外部 tokenizer 依赖」加入 §6 静态拓扑门断言，使 K10 从口头约束变成机检。
- **红线红绿灯表（基本同意，两处修）**：①「K4/K5 🟡」理由应拆为两件事——DROP+CREATE 是**替换**不是新增表（charter 须明写此语义），以及 §6 的 `row_hash_sum` 断言是否覆盖 schema 状态（现只写逐字节相等）；②「宁空勿错 🔴」范围应限定为「门后错卡」，因 §5 红测 6 已对未重建窗口设了「不得静默查询」，并非全路径无护栏。

## 4. 外审稿未覆盖的补充风险（供并入现有条款，不另立卡）

- **S1 重建原子性（并入洞 1.1，阻塞内）**：DROP+CREATE+重灌+提交前 MATCH 抽样必须在同一 SQLite 事务；中途失败不得以空表状态对外服务。落点：§3 步 5 重建协议；回滚：事务回滚即回 v2 几何。
- **S2 误召指标定义（并入洞 2.2，阻塞内）**：区分「门后错卡率」（验收上界 N）与「FTS 候选膨胀率」（只记录）；写明 N 的题库与 trigram 基线口径，避免基线 0 导致不可达验收。落点：§6 验收口径。
- **S3 ASCII 2 字母词（并入洞 2.2 红测）**：阈值 2 使 `to/of/in/is` 等首次进 FTS，须与 2 字 CJK 一并纳入高频低 IDF 误召测试。落点：§5 红测新增用例。
- **S4 复核取词口径（并入 §3 步 4，建议）**：复核对象写死为「`display_cues_json` 原文＋**非敏感**活跃别名原文」，与 E-5 隐私语义对齐，防止敏感别名经复核路径获得第二可见面。落点：§3 步 4、§5 红测 5（隐私不回退）。
